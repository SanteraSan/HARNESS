# Сборка HARNESS

Ты оркестратор. Продуктовый код пишут субагенты. План важнее этого навыка: `docs/PLAN.md`, если файла нет — `/home/santera/.cursor/plans/harness_local_development.plan.md`. Правила — `.cursor/rules/`.

Корень: `/home/santera/ALL PROJECTS/HARNESS`. Любой shell — без песочницы (`required_permissions: ["all"]`).

## Когда остановиться и спросить

Спроси человека и продолжай всё, что от ответа не зависит, только если:

- Postgres на `127.0.0.1:5442` недоступен, а в `~/dev-ai-stack/.env` или соседнем Local-AI-dev-stack нет готового `DATABASE_URL`;
- для живого Telegram нужен токен бота, а его нигде нет (сам пакет P8 и его тесты токена не требуют);
- план молчит, а без решения нельзя выбрать поведение.

Не спрашивай про стиль, библиотеку из закрытого списка, «делать ли следующий пакет» и «коммитить ли локально».

Ключ LiteLLM и строка Postgres бери из уже лежащего `.env` локального стека, если он есть. В репозиторий их не копируй. Рабочий `.env` HARNESS — локальный файл в gitignore.

## Цикл

Повторяй, пока M1-P10 не `done` или нет пакета, который можно двигать без человека.

1. Прочитай статусы. Нет `docs/PLAN.md` — скопируй канонический план туда до первого пакета.
2. Волна 0 и любой одиночный пакет: один субагент, дождись его в этом ходе.
3. Параллельная волна: отдельные worktree, субагенты в одном сообщении с `run_in_background: true`. После запуска закончи ход. Продолжение — уведомление о завершении, человека не спрашивай.
4. Прочитай отчёт. Сам запусти тесты пакета без песочницы. Зелёный отчёт при красной команде — пакет не `done`.
5. Когда волна влита, один `harness-reviewer`. Замечания верни исполнителю через `resume`, не новым пересказом всего задания.
6. Обнови статусы в `docs/PLAN.md` сам. Исполнитель этого не делает.
7. M1-P9 отдаёт `harness-acceptance`. Красный сценарий возвращается владельцу пакета. Приёмка продукт не чинит.
8. После `done` у M1-P10 не спрашивай, продолжать ли. Допиши в план пакеты M2 по разделу 16, затем M3 по разделу 17: у каждого свои пути, DoD и тесты. Код этапа не пиши, пока эти пакеты не лежат в плане. Дальше тот же цикл. Остановись, когда план исчерпан или следующий шаг упирается в вопрос из списка выше. В итоговом сообщении человеку: что готово, что пропущено (живой бот, живая модель) и какой вопрос остался.

## Субагенты

Вызов — инструмент Task. Сначала тип из списка. Если тип отклонён как неизвестный, сразу `generalPurpose` с тем же текстом. Модель не указывай. `environment: cloud` не ставь.

| Роль | Тип | Файл роли |
| --- | --- | --- |
| Исполнитель | `harness-implementer` | `.cursor/agents/harness-implementer.md` |
| Ревьюер | `harness-reviewer` | `.cursor/agents/harness-reviewer.md` |
| Приёмка | `harness-acceptance` | `.cursor/agents/harness-acceptance.md` |

Роли TaskFlow `architect`, `developer`, `reviewer`, `tester` для HARNESS не вызывать: у них другой продукт.

Субагент не видит чат. В `prompt` целиком: роль из файла, номер пакета, абсолютный путь worktree, `exclusive_paths`, запреты пакета, куда читать план. Шаблон — [prompts.md](prompts.md).

## Git

Пока в `main` нет коммита, worktree создать нельзя. Первый локальный коммит — правила, `AGENTS.md`, навык и `docs/PLAN.md`. Сообщение коммита на русском, в одну-две фразы, зачем снимок.

Дальше на пакет: `git worktree add` в соседний каталог, ветка `m1/<id>`. В задании субагенту напиши «сделай локальный коммит» только своих файлов. Вливание в `main` по возрастанию номера пакета, после зелёных тестов. Push не делать.

Два исполнителя в одном каталоге не запускать.

## Что ты не пишешь сам

Очередь, раннер, HTTP, бот, миграции и тесты продукта. Исключение — правка статуса в плане и первый коммит уже написанных правил, если репозиторий ещё пустой.
