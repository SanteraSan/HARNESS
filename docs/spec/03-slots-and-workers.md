# 03. Слоты модели и пул воркеров

## Назначение

По умолчанию один процесс `worker` и один слот модели.

Сколько слотов поднять, решает установщик. Для Qwen он записывает уже выбранное человеком `num_parallel` в `MODEL_SLOTS`. Для другой модели — её предел одновременных ответов. Хаб имя модели в это число не переводит и у Ollama `num_parallel` не читает.

Слот — право одного хода модели. Строк в таблице ровно `MODEL_SLOTS`. Процессы воркера поднимает установка, не код `worker.ts`. `runWorker` по-прежнему держит один текущий запуск на процесс и дочерние воркеры не порождает.

Один чат сериализуется. Параллельность — между разными чатами, в пределах свободных слотов и свободных процессов.

## Что в пункт не входит

Нет чтения `num_parallel` из демона модели. Нет очереди запусков внутри процесса. Нет Docker и Kubernetes как способа получить вторую копию. Нет отдельного лимита слотов для сервиса: сервис слот модели не занимает. Нет смены `008_completion_limit.sql`. Слово «слот» в том файле — про `max_completion_tokens`.

## Правила ядра

Фраза границы «Пула нет» и пункт 11 раздела 3 `PLAN.md` заменяются несколькими процессами. Число по умолчанию — 1.

**I13** сохраняется: один процесс — один текущий запуск. Внутри процесса второй `claim` не начинается, пока `Runner` не вернулся.

**I6** сохраняется. Живой `chat_id` даёт `409` и `reason: "dialog_busy"` вместе с id живого запуска. Буфер Telegram из M2 этот пункт не меняет.

**I7** сохраняется для запуска и повторяется для слота: один `UPDATE … FOR UPDATE SKIP LOCKED`, heartbeat, ноль строк значит, что лок не наш, `succeeded` не ставится.

**I8** сохраняется для запуска. Просрочка слота строку `runs` не трогает и `attempt` не меняет.

**I1** сохраняется. Захват слота живёт рядом с очередью запуска, не внутри клиента модели. Клиент модели слот не берёт сам.

## Технологии

Аренда слота повторяет аренду запуска: короткий `UPDATE`, `now()` Postgres, heartbeat, просрочка возвращает строку. Образец захвата запуска — `src/queue/run-queue.ts`. Часы процесса для `locked_until` не используются.

Пул соединений процесса остаётся `max: 4`. Слот не открывает второй пул. `statement_timeout` 15 с. Транзакция слота коммитится до `ChatModel.complete` и не держится на время модели.

Число процессов задают template units systemd, экземпляр `harness-worker@<id>.service`. `WORKER_ID=%i`. Значение по умолчанию из `hostname()` остаётся только для одного ручного `npm run worker`. Два ручных процесса без разных `WORKER_ID` — ошибка установки: они сольют локи. Код это не «лечит» порождением процессов и не добавляет файловый лок.

`MODEL_SLOTS` — целое не меньше 1, по умолчанию 1. На старте воркера `count(*)` из `model_slots` обязан совпасть. Иначе процесс выходит до захвата и до `listen` API он не относится: проверку делает процесс воркера.

systemd: `NoNewPrivileges=yes`, `ProtectSystem=strict`. `ReadWritePaths` воркера не содержит `FILE_ROOT` и `BLOB_ROOT`. Путь юнита выбирает установщик.

## Протокол аренды

Миграция `migrations/009_model_slots.sql`. Этот документ файл не создаёт. `001` … `008` не меняются.

```sql
create table model_slots (
  slot_index integer primary key check (slot_index >= 1),
  locked_by text,
  locked_until timestamptz,
  run_id uuid
);
```

Строки `1..N` вставляет установщик отдельным SQL, не эта миграция. Пока строка занята, число не меняют. Удалять строку с непустым `locked_by` нельзя.

Снятие просрочки не трогает `runs`. Это отдельный короткий оператор, не часть `UPDATE` захвата:

```sql
update model_slots
set locked_by = null,
    locked_until = null,
    run_id = null
where locked_until is not null
  and locked_until < now();
```

Захват — один оператор. В коде значения идут помеченным шаблоном `postgres`, не склейкой строк. Ниже форма, не текст для `sql.unsafe`:

```sql
update model_slots
set locked_by = $worker,
    locked_until = now() + make_interval(secs => $lease),
    run_id = $run
where slot_index = (
  select slot_index
  from model_slots
  where locked_by is null
  order by slot_index
  for update skip locked
  limit 1
)
returning slot_index;
```

`$lease` — тот же `LEASE_SECONDS`, что у запуска (120). Отдельного срока слота нет.

Heartbeat слота ставит `locked_until = now() + make_interval(secs => $lease)` только при том же `locked_by`, том же `run_id` и непустом локе. Ноль строк — слот уже не наш, функция возвращает `false`.

Отпускание — один `UPDATE` в те же условия, поля `locked_by`, `locked_until` и `run_id` становятся null. Ноль строк — слот уже не наш. Отпускание всё равно не ставит запуску `succeeded`.

Ожидание свободного слота крутится с паузой 1 с и с heartbeat запуска. Модель в этой паузе не вызывается. Клиенту отказ не отправляется: id запуска он уже получил.

Интервал heartbeat слота — `HEARTBEAT_SECONDS` (15), пока идёт `ChatModel.complete`. После ответа шлюза heartbeat слота останавливается и слот отпускается до любого HTTP сервиса.

## Данные и порядок

Порядок относительно захвата запуска:

1. Постановка клиента уже закоммичена отдельной транзакцией. Воркер к ней не возвращается.
2. `reapExpired` запускает просроченные `runs` по правилам **I8**. Просроченные `model_slots` снимаются своим оператором и `runs` не меняют.
3. `claimNext` — один `UPDATE` запуска. Коммит до модели и до слота.
4. Heartbeat запуска. `false` — выход без `finish`.
5. Захват слота. Коммит до модели. Нет строки — пауза 1 с, heartbeat запуска, снова захват слота.
6. `ChatModel.complete`. Соединение базы этот вызов не держит. Heartbeat запуска и heartbeat слота идут короткими операторами.
7. Ответ шлюза записан в суммы токенов так же, как сейчас, только пока лок запуска наш. Слот отпускается здесь, до разбора инструментов и до HTTP сервиса.
8. Сервис слот не занимает. Долгое чтение файла не держит право на модель.

Два разных `chat_id` могут идти двумя процессами. Одновременных ответов модели не больше числа свободных слотов. Если процессов больше, чем слотов, лишний процесс держит свой запуск и ждёт слот. Если слотов больше, чем процессов, лишние строки простаивают. Хаб второе число из первого не выводит.

Потеря heartbeat слота не ставит запуск в `succeeded`. Просрочка слота только освобождает строку. Другой воркер может взять её следующим захватом.

Чужой `WORKER_ID` не продлевает слот: условие heartbeat требует тот же `locked_by`.

`SIGTERM` и `SIGINT` перестают брать новые запуски. Обработчик сигнала не ставит `succeeded`. Просроченную аренду запуска и слота снимет следующий reap.

## Отказы

Нет свободного слота — ожидание, не отказ клиенту и не `failed`.

Расхождение `MODEL_SLOTS` и `count(*)` — процесс воркера выходит до захвата. В лог код конфигурации, без `DATABASE_URL`.

Чужой heartbeat возвращает `false` и чужой `locked_until` не двигает.

Ответ модели пришёл после потери слота: текст в `succeeded` не записывается. Если лок запуска жив, статус `failed`, ошибка `slot_lost`. Если лок запуска тоже потерян, `finish` не вызывается и новые шаги не пишутся.

Потеря слота после того, как он уже отпущен штатно, сервису не видна: сервис слот не держит.

Два запуска с одним `chat_id` по-прежнему не создаются. Второй `POST /v1/runs` получает `409`, `reason: "dialog_busy"`, `id` живого.

## Безопасность

Разработка. Тест слотов — два реальных соединения к базе, имя которой кончается на `_test`. Мок модуля `postgres` не доказывает `SKIP LOCKED`. В тесте нет кода, который читает имя модели и сам решает, сколько строк вставить. Число строк задаёт фикстура.

Эксплуатация. Юниты воркера одинаковые, кроме `WORKER_ID`. Каждый смотрит только в `127.0.0.1` к Postgres и к LiteLLM. `ReadWritePaths` пуст относительно `FILE_ROOT` и `BLOB_ROOT`. Перезапуск одного экземпляра не помечает его запуск успешным.

Смена `MODEL_SLOTS` — действие человека: остановить воркеры, поменять свободные строки, поменять конфиг, запустить. Удалять строку с живым `locked_by` нельзя. Хаб сам строки не добавляет и не удаляет.

В лог слота входят `run_id`, `slot_index` и код отказа. Не входит текст модели и `Authorization`.

## Тесты

- два соединения берут два разных `slot_index` и не один и тот же;
- третий захват при двух строках получает пусто;
- просроченный `locked_until` снова свободен, и `runs.status` не стал `succeeded`;
- heartbeat чужого воркера возвращает `false` и срок не продлевает;
- конфиг `2` при одной строке не пускает цикл захвата;
- в коде захвата слота один `for update skip locked` внутри одного `UPDATE`;
- HTTP сервиса начинается только после отпускания слота;
- два запуска с одним `chat_id` не исполняются параллельно;
- обработчик `SIGTERM` не вызывает `finish` со статусом `succeeded`;
- имя модели в тесте не выбирает число вставок.

## Критерии готовности

По умолчанию один процесс и одна строка, если установщик вставил одну строку и `MODEL_SLOTS` равен 1. Хаб не вычисляет предел модели. **I13** соблюдён. **I6** соблюдён. Потеря аренды слота не даёт `succeeded`. Сервис слот не занимает. `008_completion_limit.sql` не изменён.
