# 07. Git и CI

## Назначение

Работа входит в `dev`, `stage` и `prod` только через pull request. Прямой push, force-push и удаление этих веток запрещены. Обхода администратора нет. Отдельное approving review не требуется: человек один, CodeRabbit не одобряет.

Ветка `main` в этом контуре не участвует. Её не переименовывают, не включают в ruleset и не связывают с `dev`, `stage` и `prod`. Обновляет её человек сам.

Код продукта этот пункт не меняет. Спецификация фиксирует целевое состояние и то, что уже есть в репозитории. Новый пакет ворота не ослабляет.

## Что уже есть

Сверено с `dev` после слияния PR #5 (`3fa9259`, 11 ноября 2026) и с ruleset репозитория `SanteraSan/HARNESS`.

### Ветки и ruleset

Ruleset `dev-stage-prod-pr-only` включён (`enforcement: active`). В него входят только `refs/heads/dev`, `refs/heads/stage`, `refs/heads/prod`. Список обхода пуст. Классическая branch protection на `dev` не включена: API защиты ветки отвечает, что ветка не защищена. Граница — ruleset, не второй механизм.

Правила ruleset:

- удаление ветки запрещено;
- force-push запрещён (`non_fast_forward`);
- изменение только через pull request;
- `required_approving_review_count` равен 0;
- погашение одобрений после нового push не включено;
- обязательное закрытие тредов не включено;
- методы слияния — merge, squash и rebase;
- `strict_required_status_checks_policy` выключен: свежесть ветки относительно базы ruleset не требует;
- обязательные проверки: `tests`, `trivy`, `build`, `branch-flow`.

Проверки `sonar` в списке нет. На pull request job `sonar` пропускается, и пропуск не красит сборку. Делать `sonar` обязательным на PR нельзя: SonarQube Community Build pull request не анализирует.

Агент этот ruleset не ослабляет. Не добавляет обход, не поднимает число одобрений, не вносит `main`, не снимает запрет force-push.

### Поток веток

Короткая ветка этого репозитория сливается в `dev` pull request. Дальше отдельный pull request `dev` → `stage` и отдельный pull request `stage` → `prod`. Прямой push в любую из трёх веток запрещён.

Job `branch-flow` в `.github/workflows/ci.yml` на `pull_request`:

- голова из другого репозитория падает;
- база `dev` принимает любую голову этого репозитория;
- база `stage` принимает только голову `dev`;
- база `prod` принимает только голову `stage`;
- иная база падает.

На `push` job пропускается и в проверки push не входит. Секретов у job нет. Он идёт на `ubuntu-latest`.

### Workflow

Файл `.github/workflows/ci.yml`. События: `push` и `pull_request` в `dev`, `stage`, `prod`. События `pull_request_target` нет.

Порядок job: `tests` → `sonar` (только push) → `trivy` → `build`. `branch-flow` от этой цепочки не зависит.

`permissions` workflow: `contents: read`, `actions: write`. Запись actions нужна загрузке артефактов. Job `branch-flow` сужает себя до `contents: read`.

`persist-credentials: false` стоит на каждом `actions/checkout`. Action закреплены полным SHA коммита. Плавающий тег не ставится. SHA лежат в workflow, этот файл их не копирует.

Форк не запускает на self-hosted раннере `harness-sonar` job с секретами. Условие `tests`: push, либо pull request, у которого голова из этого репозитория. Иначе `tests` пропускается. Пропущенные `tests` не пускают `trivy`. Падение `tests` или `sonar` тоже не пускает `trivy`. `build` зависит от `trivy`.

Раннер `harness-sonar` нужен `tests`, `sonar`, `trivy` и `build`, потому что SonarQube и тестовая база на той же машине и слушают localhost. Весь CI на GitHub-hosted не переносится. `branch-flow` остаётся на `ubuntu-latest`: секретов и localhost ему не нужно.

`npm ci` в `tests` и `build` идёт с `HUSKY=0`. Установка на раннере хуки не ставит и ворота не подменяет.

Секреты job `tests`: `DATABASE_URL` и `HARNESS_TEST_DATABASE_URL`. Оба указывают на базу с суффиксом `_test`, не на боевую `harness`. Значения в этот файл не пишутся. Имя в CI, которое не кончается на `_test`, не используется.

### Тесты и покрытие

Job `tests` выполняет `npm run test:coverage`. Отчёт `coverage/lcov.info` загружается артефактом `lcov`. Пустой файл — ошибка шага. В git отчёт не входит.

### SonarQube

Community Build, режим MQR. Проекты `harness-dev`, `harness-stage`, `harness-prod`. Workflow подставляет ключ `harness-${{ github.ref_name }}` и только на push в эти три ветки. На pull request job пропускается, а не красится в зелёный и не красится в красный.

Сканер ждёт ворота: `sonar.qualitygate.wait=true`, таймаут `sonar.qualitygate.timeout=300`. Переменная окружения `GITHUB_ACTIONS` на шаге сканера равна `false`, чтобы сканер не подставил `sonar.branch.name`: Community Build этот параметр отклоняет. Украшения pull request нет.

Адрес сервера — переменная GitHub `SONAR_HOST_URL`. Токен — секрет `SONAR_TOKEN`. В workflow и в `sonar-project.properties` адреса нет. `sonar-project.properties` задаёт источники `src`, тесты `test`, кодировку UTF-8 и путь `sonar.javascript.lcov.reportPaths=coverage/lcov.info`.

Ворота смотрят новый код. Сборка на push красная, если на новом коде верно любое условие:

- баг больше нуля или уязвимость больше нуля;
- рейтинг надёжности хуже A или рейтинг безопасности хуже A;
- security hotspots разобраны меньше чем на 100%;
- покрытие ниже 80%;
- дублирование выше 3%.

Оценка сопровождаемости и условие «любое новое замечание» в ворота не входят. Покрытие берётся из `coverage/lcov.info`, который пишет `npm run test:coverage` до скана. Нет отчёта — шаг проверки файла красный, скан с пустым покрытием не начинается.

Имя юнита Sonar, путь к нему, порт и домашний каталог в этот файл не пишутся. Их нет в workflow.

### Trivy

Версия 0.76.2. Бинарь качается в каталог job, сверяется sha256 из workflow, без sudo и без Docker. Суммы архивов лежат в `ci.yml`. Образ не сканируется: Docker этот пункт не требует.

Порядок шагов внутри job:

1. SBOM: `trivy fs --scanners vuln --format cyclonedx --output sbom.cdx.json` с пропуском каталогов `node_modules`, `coverage`, `workspace`. Файл создаётся до сканов, которые могут кончиться ненулём. Пустой файл — ошибка шага.
2. Уязвимости: `--scanners vuln --severity HIGH,CRITICAL --exit-code 1`. `MEDIUM` и ниже сборку не ломают. `--ignore-unfixed` нет.
3. Секреты: `--scanners secret` с конфигом `trivy-secret.yaml`. Отчёт пишется во временный файл job, в лог попадают путь, строка и код правила, не само значение. Файл отчёта удаляется. Артефактом отчёт секретов не становится.
4. Загрузка SBOM, если файл уже создан и workflow не отменён, в том числе после красного скана. Job при красном скане остаётся красным. `retention-days: 1`. GitHub не принимает срок в часах, минимум — сутки. В архив попадает только `sbom.cdx.json`.

`trivy-secret.yaml` выключает встроенные allow-правила `tests`, `markdown` и `examples`. Узкого исключения на фикстуру в этом файле нет: узнаваемый секрет в тесте, в markdown и в `.env.example` валит job. Поэтому спецификация и фикстуры не содержат боевых ключей и длинных секретоподобных строк.

`.trivyignore` этим пунктом не заводится. Новая строка игнора, если она появится, видна в diff. Без записи человека, зачем она, её не добавляют.

### Сборка

Job `build` зависит от `trivy` и запускает `./node_modules/.bin/tsc --noEmit`. Скрипта production-сборки в `package.json` нет. Отдельного бандла нет. Секреты базы в job не входят.

### Husky

`husky` 9.1.7 в devDependencies. Скрипт `prepare` — `husky`. Это уже в `dev`: PR #5 слит.

`pre-commit` запускает `tsc --noEmit` и ESLint по файлам индекса. Скрипт `.husky/pre-commit-eslint.mjs` читает индекс через `git diff --cached -z` и передаёт имена массивом в ESLint. `git` вызывается `execFile` с постоянным списком аргументов, без оболочки. Полные тесты, Sonar и Trivy в хук не входят. Файла `pre-push` нет.

`HUSKY=0` в CI остаётся. Обход хука флагом `--no-verify` локально возможен и границей не считается. Граница — ruleset и красные job.

Правила `security/detect-child-process`, `security/detect-eval-with-expression`, `security/detect-non-literal-regexp` и `security/detect-unsafe-regex` остаются ошибками. Второй набор ESLint не заводится.

### Сортировка миграций

Уже в `src/db/migrate.ts`. Имена `*.sql` сортируются `localeCompare` с локалью `en` и `numeric: true`. Если результат нулевой, полные имена сравниваются по кодам UTF-16, операторами `<` и `>`. Порядок не зависит от локали машины и от порядка каталога. Менять компаратор этот пункт не просит. Новая миграция — новый файл, старые файлы не переименовываются.

### CodeRabbit

Приложение подключено и пишет замечания. Базу `dev` человек включает в кабинете сам. Этот файл кабинет не переключает.

Требуемые права приложения: Contents Read, Pull requests Read and write. Администрирование и право одобрять pull request не давать. Ruleset не считает CodeRabbit тем, кто одобряет: число обязательных одобрений равно нулю, отдельного approving review нет. Проверки `ai-review` в ruleset нет.

Живой список прав установки в этот файл не копируется: для чтения нужен токен приложения, его здесь нет.

### Bandit

Шаг Bandit в pipeline не входит. Это сознательно. Репозиторий на TypeScript, близкую проверку делает `eslint-plugin-security`. Пустой зелёный шаг «нет Python» не добавляется. Появление `.py` само по себе Bandit не включает: это было бы новое решение, и этот файл его не принимает.

`docs/EXPANSION.md` в пункте 7 ещё говорит про Bandit, про `pre-push` с тестами и про обязательное approving review человека. Для репозитория HARNESS действует этот файл и текущий workflow. Те три решения не реализуются и в workflow не возвращаются. `EXPANSION.md` спецификация не переписывает.

## Чего в пункте нет

Нет деплоя. Нет продукта туннеля. Нет выбора оболочки. Нет ключа модели в секретах репозитория. Нет URL SonarQube. Нет юнита и порта Sonar. Нет второго ESLint. Нет обязательного Docker и Kubernetes. Нет переноса CI на GitHub-hosted.

## Правила ядра

**I15** сохраняется для runtime. `husky` и `@vitest/coverage-v8` уже стоят как devDependencies. Новая runtime-зависимость этим пунктом не оправдывается.

**I17** сохраняется. CI не правит `src/contracts/**` и применённые миграции.

**I18** сохраняется. Упавший тест не ослабляют, чтобы job стал зелёным. `--exit-zero` у сканеров не ставится.

**I20** сохраняется. Секреты CI не печатаются. В репозиторий не коммитятся `.env`, токены и дампы.

Тестовая база в CI кончается на `_test`. `DROP DATABASE` и команды против боевой `harness` из теста запрещены, как в правиле базы.

## Отказы

Упал `tests` — `sonar` и `trivy` не стартуют как успешное продолжение. Упал `sonar` на push — `trivy` не стартует. На pull request пропуск `sonar` — не падение, `trivy` идёт после успешных `tests`.

`HIGH` или `CRITICAL` у Trivy закрывают слияние. Находка секрета тоже. Недоступный Sonar на push красит шаг, пропуском не считается. `hotfix` эти job не отключает.

Форк падает на `branch-flow` и не получает секреты раннера.

Красные ворота не обходятся force-push и не обходятся прямым push. Падение ворот уже запущенные процессы хаба не трогает.

## Безопасность

Разработка. Workflow не содержит значений секретов. В diff зависимостей человек смотрит новый пакет. `eslint-disable` без причины в отчёте PR не оставляется. Фикстура не делается похожей на боевой ключ ради зелёного сканера.

Эксплуатация. Секреты CI живут в GitHub, не в юнитах хаба и не в `BLOB_ROOT`. Ротация `SONAR_TOKEN` не крутит `HARNESS_API_TOKEN` и не крутит секрет сервиса. Артефакт SBOM перечисляет версии пакетов. Туда не кладут `.env` и отчёт секретного сканера.

Боевая база `harness` в CI не используется. Дерево на раннере не должно содержать боевой `.env` разработчика. Job Node ставит runtime в каталог инструментов раннера и домашний каталог разработчика раннеру не отдаёт.

## Тесты

Живой GitHub и живой Sonar в `npm test` не требуются. Проверки этого пункта уже выражены workflow и ruleset. Агент, который их трогает, обязан сохранить наблюдаемое поведение:

- в workflow порядок `needs`: `sonar` ждёт `tests`, `trivy` ждёт `tests` и `sonar`, `build` ждёт `trivy`;
- `sonar` не стартует на `pull_request`;
- `branch-flow` отвергает форк, голову не из `dev` в `stage` и голову не из `stage` в `prod`;
- `pre-commit` на файле с ошибкой ESLint кончается ненулём и не собирает оболочку из имени файла;
- в workflow нет `0.0.0.0` как адреса слушателя и нет `rejectUnauthorized: false`;
- в workflow нет шага Bandit;
- компаратор миграций отдаёт `02` раньше `2` за счёт numeric, а при равном numeric сравнивает полные имена по UTF-16.

## Критерии готовности

Прямой push, force-push и удаление `dev`, `stage` и `prod` закрыты действующим ruleset, обход пуст. Обязательные проверки pull request — `tests`, `trivy`, `build`, `branch-flow`. `sonar` на PR не обязателен. Скан Sonar идёт на push в три ветки, ворота — по новому коду, условия записаны выше. `build` — это `tsc --noEmit`. Trivy 0.76.2 падает на `HIGH` и `CRITICAL`, ищет секреты без публикации отчёта и пишет SBOM CycloneDX на одни сутки. Husky 9.1.7 стоит, `pre-commit` гоняет типы и ESLint, полные тесты в хук не входят. Bandit не используется. Ветка `main` в ruleset не входит.
