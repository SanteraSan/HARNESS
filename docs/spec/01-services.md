# 01. Сервисы вместо зашитых инструментов

## Назначение

`read_file`, `list_dir` и `record_note` уходят из процесса воркера в один файловый сервис. Воркер их больше не вызывает сам. Раннер, после коммита захвата, передаёт имя, аргументы и идентификаторы запуска и получает короткий текст.

Файловый сервис — репозиторий `https://github.com/SanteraSan/harness-files` и отдельный процесс. Он единственный, кто открывает `FILE_ROOT`. Хаб после выноса этот каталог не читает и не пишет. Кода сервиса в репозитории HARNESS нет. Реализация в `harness-files` ещё не начата. Хаб знает контракт `harness.tool.v1` и локальный манифест.

Jira и длинный текст подключаются тем же конвертом. Ниже они примеры, не задания на интеграцию.

## Что в пункт не входит

Нет экрана сервиса. Нет клиента Jira. Нет второй модели внутри хаба. Нет подхвата инструментов по сети на старте. Нет пула потоков внутри одного процесса Node. Нет переноса `create_subtask`, `approve`, кронов, секретов коннекторов и `ClaudeSdkRunner`.

Пустой список инструментов хода `coder-cloud` этот пункт не реализует: это пакет M3-P7, в коде его ещё нет. Когда он сделан, у такого хода сервиса нет, даже если имя есть в манифесте. Поле `reasoning_effort` этот пункт не добавляет.

Репозиторий сервиса — `https://github.com/SanteraSan/harness-files`. Реализация в нём ещё не начата. Репозитории Jira и длинного текста не создаются.

## Правила ядра

Меняется **I12** для трёх имён: их исполняет файловый сервис, вызов идёт из раннера. **I19** для `FILE_ROOT` переезжает в этот сервис. Фраза «пула нет» заменяется несколькими процессами `worker` по `03-slots-and-workers.md`. Внутри одного процесса пула по-прежнему нет (**I13**).

Сохраняются **I1**, **I2**, **I3**, **I4**, **I7**, **I13**, **I15**, **I18**, **I20**. Очередь не импортирует клиент сервиса. Запрет имён сильнее allowlist и сильнее манифеста. `redact` стоит до журнала и до следующего сообщения модели. JSON инструмента в тексте не вызывает HTTP. Ошибка инструмента не роняет запуск. Потеря лока не ставит `succeeded`.

`record_note` остаётся `effect: "write"`. Возвращать его к `effect: "read"` нельзя.

В `package.json` хаба не добавляются пакеты. Клиент — `fetch` Node 22. Проверка конверта — ручной zod, уже стоящий в хабе.

## Технологии

Вызов — HTTP JSON на `127.0.0.1`. gRPC не берётся: это второй стек и новый список зависимостей. stdio не берётся: хаб тогда порождал бы процесс сервиса, а строка оболочки для инструментов запрещена.

Клиент — `fetch`. `redirect: "error"`, чтобы ответ `3xx` не уводил хаб на другой хост. Таймаут — `AbortSignal.timeout`. Тело ответа читается с потолком `SERVICE_RESPONSE_BYTES` (393627 байт): худший JSON успешного текста файла в 64 КиБ плюс конверт. Раннер принимает этот потолок целиком, затем `prepareToolResultText` режет текст модели до 8000 кодпоинтов. Лишнее обрывается, в модель не попадает.

Хаб порт не угадывает. Порт входит в `base_url` манифеста. Секрета в файле манифеста нет: хаб читает bearer из переменной окружения, имя которой записано в `auth.env`. `auth.type` `none` только для `http://127.0.0.1` с портом.

Если адрес не лупбэк, в манифесте литерал частного IPv4, не имя DNS. Схема `https`. `rejectUnauthorized` остаётся `true`. `checkServerIdentity` сверяет `fingerprint256` сертификата с `tls_fingerprint256` из манифеста через `timingSafeEqual` по 32 байтам. IPv6, имя `localhost` и `0.0.0.0` в `base_url` делают манифест недействительным. Битый манифест останавливает процесс воркера до захвата.

Файловый сервис на лупбэке слушает только `127.0.0.1`. HTTP поднимается через `node:http`, без Hono и без второго фреймворка. Зависимости runtime сервиса: Node 22, `postgres` 3.4.9, `zod` 4.6.7, `pino` 10.4.0. Версии не ослабляются до `*` и `latest`. Dev-цепочка сервиса совпадает с хабом по именам `typescript`, `tsx`, `vitest`, `@types/node`, `eslint`, `typescript-eslint`, `eslint-plugin-security`, `prettier`. ORM, Redis, LangGraph, Claude Agent SDK и Ajv сервису не ставятся.

База сервиса — тот же экземпляр Postgres, что у хаба (`127.0.0.1:5442` в `PLAN.md`), отдельная база `harness_files`, роль `harness_files_app`. Пароль в спецификацию не пишется. Роль не имеет `CONNECT` к базе `harness` и не читает `runs`. Тестовая база — `harness_files_test`. URL сервиса лежит в его окружении, не в `DATABASE_URL` хаба.

## Протокол

Версия — `harness.tool.v1`. Хаб вызывает:

`POST /v1/tools/{name}`

`{name}` — один сегмент пути. Сравнение с именем в теле побайтовое, после одного декодирования percent-encoding. Слэш, `.` и `..` в сегменте не являются именем инструмента. Совпадает с телом и с манифестом — вызов. Иначе сервис отвечает `400` и `reason: "invalid_body"`, если сегмент разобран, но не равен телу, и `404` и `reason: "unknown_tool"`, если имени нет у сервиса.

Заголовки запроса:

- `Authorization: Bearer <секрет этого сервиса>`.
- `Content-Type: application/json; charset=utf-8`.
- `X-Contract-Version: harness.tool.v1`. Значение обязано совпасть с полем `contract`. Иначе `400` и `reason: "unsupported_version"`.
- Для `effect: "write"` обязателен ровно один `Idempotency-Key`. Для `effect: "read"` заголовок можно прислать, строку идемпотентности сервис не создаёт. Кривой заголовок и на чтении даёт `400`.

`Idempotency-Key` — одна quoted-string из structured fields, без параметров:

```http
Idempotency-Key: "00000000-0000-4000-8000-000000000010:call_1"
```

Внутри кавычек ровно `<run_id>:<tool_call_id>`. `run_id` — uuid в нижнем регистре. `tool_call_id` — 1..128 символов из `A-Z`, `a-z`, `0-9`, `_`, `-`. Двоеточие в `tool_call_id` запрещено, чтобы разрез был однозначным. Повтор заголовка, параметры после кавычек и несовпадение с полями тела — `400` и `reason: "invalid_body"`.

Тело, других полей нет:

```json
{
  "contract": "harness.tool.v1",
  "run_id": "00000000-0000-4000-8000-000000000010",
  "tool_call_id": "call_1",
  "agent_id": "00000000-0000-4000-8000-000000000001",
  "name": "read_file",
  "arguments": { "path": "notes/a.txt" }
}
```

`agent_id` — uuid. `chat_id` в теле нет. Неизвестное поле — `400` и `reason: "unknown_field"`. Другой `contract` — `400` и `reason: "unsupported_version"`. Тело больше 32 КиБ — `413` и `reason: "payload_too_large"`. Ключи `__proto__`, `constructor`, `prototype` — `unknown_field`.

Успех, HTTP `200`:

```json
{
  "contract": "harness.tool.v1",
  "ok": true,
  "text": "notes/a.txt",
  "truncated": false,
  "duration_ms": 4,
  "blobs": []
}
```

Ожидаемая ошибка инструмента тоже HTTP `200`. Запуск хаба жив. Поля `text` нет. `blobs` — пустой массив. Обязательны `error` и `error_code`. `error` — 1..200 кодпоинтов без управляющих символов и без стека:

```json
{
  "contract": "harness.tool.v1",
  "ok": false,
  "error": "path escapes root",
  "error_code": "forbidden",
  "truncated": false,
  "duration_ms": 2,
  "blobs": []
}
```

При `ok: false` в роль tool идёт строка `error` после той же подготовки, что и `text`: скрытые символы снимаются, хвост длиннее 8000 кодпоинтов отрезается. Сырой JSON в модель не кладётся.

| Ситуация | `error` | `error_code` |
| --- | --- | --- |
| path escapes root и запрет пути | `path escapes root` | `forbidden` |
| not found | `not found` | `not_found` |
| not a file и binary content | `not a file` или `binary content` | `invalid_args` |
| file exists | `file exists` | `conflict` |
| слишком большой файл | `file too large` | `too_large` |

`duration_ms` — целое 0..600000. `text` на успехе — строка не длиннее 65536 кодпоинтов. `blobs` — массив uuid, не длиннее 8, без повторов. Поля `prompt_tokens`, `completion_tokens`, `cost_usd` и любое иное поле контракт не содержит. Хаб такой ответ модели не отдаёт и пишет шаг с `error: "unknown_field"`. Суммы токенов запуска не меняются.

Ошибка HTTP сервиса, других полей нет:

```json
{ "reason": "invalid_body" }
```

| Код | `reason` | Смысл |
| --- | --- | --- |
| 400 | `invalid_body` | тело, путь или ключ |
| 400 | `unknown_field` | лишнее поле |
| 400 | `unsupported_version` | чужой `contract` или заголовок версии |
| 401 | `unauthorized` | bearer |
| 404 | `unknown_tool` | имени нет у этого сервиса |
| 409 | `idempotency_conflict` | тот же ключ, другой хеш |
| 409 | `idempotency_in_progress` | тот же ключ ещё выполняется и ответа нет; не окончательный отказ, вызывающий повторяет |
| 413 | `payload_too_large` | тело больше 32 КиБ |

`GET /health` сервиса без секрета возвращает `{ "ok": true }` и `nosniff`. В теле нет версии пакетов и нет путей. Других маршрутов у сервиса нет.

### Аргументы трёх имён

Процесс воркера пока ещё требует поле `idempotency_key` у локального инструмента. В сервис оно не уходит. Точка входа контракта снимает его с копии аргументов до проверки и до хеша. В аргументы контракта `record_note` ключ не возвращается. Сервис это поле не принимает: осталось — `unknown_field`.

`read_file`, `effect: "read"`, `accepts_blobs: false`:

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["path"],
  "properties": {
    "path": { "type": "string", "minLength": 1, "maxLength": 4096 }
  }
}
```

Успех: `text` — UTF-8 файла, не больше 64 КиБ. Файл толще лимита даёт усечённый текст и `truncated: true`. Незавершённый UTF-8 на границе чтения снимается, и это не `binary content`. Каталог, бинарное содержимое и путь снаружи — `"ok": false`. Текст ошибки: `not a file`, `binary content` или `path escapes root`. Коды — в таблице выше. Отказ `file too large` — отдельный случай, когда сервис не отдаёт усечённый текст.

`list_dir`, `effect: "read"`, `accepts_blobs: false`. Поле `path` необязательно. Без него корень `FILE_ROOT`. Один уровень, без рекурсии. Каталог снаружи и симлинк каталога наружу — `path escapes root`. Имена сортируются сравнением UTF-16 (`<` и `>` JavaScript). Каталог в тексте заканчивается на `/`. Обычное имя и симлинк — без слэша: симлинк не разыменовывается. Строки склеены `\n`, без перевода строки в конце. Сервис добавляет имена, пока следующий элемент не превысит 8000 кодпоинтов текста результата, и тогда `truncated` становится `true`. Уже добавленные имена остаются, имя посередине не режется. Пустой каталог: `truncated` false и пустой текст. Полный список без обрезки контракт не обещает.

`record_note`, `effect: "write"`, `accepts_blobs: false`:

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["path", "text"],
  "properties": {
    "path": { "type": "string", "minLength": 1, "maxLength": 4096 },
    "text": { "type": "string", "minLength": 1, "maxLength": 12085 }
  }
}
```

Путь относительный. Первый сегмент только `out`. Сегмент не пустой, не `.`, не `..`, не `.record-note`, не длиннее 255, без NUL. Абсолютный путь и обратный слэш отвергаются. Каталог `FILE_ROOT/out` не является симлинком. Файл пишется только внутри него. Каталоги под `out` создаются. Если файл уже есть, его не перезаписывают: ошибка `file exists`, код `conflict`. Успех: `text` равен `wrote ` и сегментам через `/`, например `wrote out/a.txt`. `truncated` — `false`.

`maxLength` текста — 12085 кодпоинтов. Худший канонический POST без пробелов умещается в 32768 байт ровно: конверт с `service` из 64 символов и `tool_call_id` из 128, `path` из 4096 кавычек, `text` из кавычек. Кавычка и перевод строки кодируются двумя байтами. На один кодпоинт длиннее тело уже 32770 байт и не проходит. Файл на диске по-прежнему не толще 64 КиБ UTF-8. Старые файлы `FILE_ROOT/out/.record-note` не импортируются.

### Канонический хеш записи

Отпечаток — SHA-256 канонического тела запроса, 32 байта. В теле нет секрета и нет способности. Способность, если она когда-нибудь есть у другого инструмента, идёт заголовком и в хеш не входит.

Канон: UTF-8, без пробелов между лексемами, ключи объекта по байтам UTF-8, порядок массива сохранён, строки как у `JSON.stringify`. Конечное целое в безопасном диапазоне — без дроби и без экспоненты. `-0` пишется как `0`. `NaN` и `Infinity` — `invalid_body` до хеша. Повтор ключа в одном объекте — `invalid_body`.

## Данные и порядок

Манифест перечисляет сервис `files`, `base_url`, имена, `effect`, описание, схему аргументов и отпечаток TLS, если адрес не лупбэк. Секрета в манифесте нет. Форма файла — в `02-contract.md`.

Порядок одного хода, после того как постановка уже закоммичена:

1. Воркер делает `reapExpired` и один `claimNext`. Оператор захвата коммитится сам. Модель ещё не вызвана.
2. Стартует heartbeat запуска каждые 15 с. `false` — выход без `finish` и без новых шагов.
3. Перед `ChatModel.complete` захватывается слот. Слот отпускается сразу после ответа шлюза и до HTTP сервиса. Подробности — в `03-slots-and-workers.md`.
4. `interpretModelOutput`. Ветка `parse_error` сервис не вызывает.
5. Для каждого `tool_calls[].id`: запрет, затем allowlist агента, затем имя из манифеста. Иначе шаг `policy_deny` и HTTP нет. `tool_call_id` вне алфавита выше — шаг `tool_result` с `invalid arguments`, HTTP нет.
6. Аргументы длиннее 32 КиБ не парсятся. Хаб снимает `idempotency_key` и проверяет копию ручным zod по схеме манифеста. Не сошлась — `invalid arguments`, HTTP нет.
7. Соединение базы к этому моменту не держит транзакцию. `fetch` идёт со своим таймаутом: 30 с на чтение, 60 с на запись.
8. Ответ проходит строгую схему. При `ok: true` в модель идёт `text`, при `ok: false` — строка `error`. Оба проходят одну подготовку и режутся до 8000 кодпоинтов. Сырой JSON в модель не кладётся. Если сервис прислал `truncated: true` или хаб отрезал хвост, в модель уходит уже резаный текст. Затем `redact`. Выдержка журнала — не длиннее 2000 кодпоинтов.
9. Для вызова сервиса `request_excerpt` — имя инструмента, пробел и 64 hex-символа SHA-256 канонического тела. Сырой JSON аргументов в выдержку и в pino не пишется.
10. Колонки `run_steps.duration_ms` нет, миграция под неё не создаётся. Шаг сервиса это поле в SQL не пишет. Длительность можно писать в лог, не в базу. В суммы `prompt_tokens` и `completion_tokens` поле ответа не входит. Для локального провайдера `cost_usd` остаётся 0.
11. `finish` возможен только при своём `locked_by` и `status = 'running'`.

Токены по-прежнему суммирует раннер из `usage` ответа шлюза. Сервис сообщает результат и `duration_ms` в теле ответа. В `run_steps` хаб это число не пишет, пока колонки нет.

Журнал идемпотентности живёт в базе сервиса, не в `FILE_ROOT`:

- `idempotency_key` — текст `<run_id>:<tool_call_id>`;
- `body_sha256` — 32 байта;
- `state` — `started` или `done`;
- сохранённый ответ;
- `created_at` от `now()`.

Порядок успешной записи, по которому потом писать сервис. Базу здесь не заводят. Сначала файл устойчив на диске: каталоги под `out` уже есть, существующий файл не перезаписан. Затем в строке сохранён ответ. Затем строка переведена в `done`. И только потом HTTP. Повтор ключа при уже сохранённом `done` и том же хеше возвращает этот ответ, второй файл не создаётся. Другой хеш — `409` `idempotency_conflict` без записи, и это окончательный отказ: повторно не отправляется.

Живой `started`, если ответа ещё нет, не отдаёт `409` как окончательный отказ. Вызывающий повторяет тот же ключ и тот же хеш. Повтор второй файл не создаёт: если файл этого ключа уже устойчив, повтор дописывает сохранённый ответ и `done`, затем отдаёт его. Чтение эту таблицу не трогает. Удаление строк старше 72 часов — не больше 20 за один следующий вызов записи. Отдельный крон не заводится.

Потеря аренды запуска посередине HTTP: сокет обрывается, `finish` не вызывается. Запись на сервисе может успеть завершиться. Повтор того же `tool_call_id` безопасен. Повтор всего запуска после reaper — новый ход модели и новый `tool_call_id`, значит новый ключ. Подменять ключ хешем аргументов нельзя.

`provider = external` по-прежнему выбирает `ClaudeSdkRunner`. Пока клиент SDK не установлен, ветка падает с `sdk_not_installed`. Три файловых имени через неё не исполняются внутри воркера.

## Отказы

Таймаут и обрыв соединения — ошибка инструмента, запуск жив. Для записи хаб повторяет один раз тот же ключ и тот же хеш. Для чтения повтора нет. `WRITE_TRANSPORT_ATTEMPTS` равен 2: первая попытка и один повтор.

`409` с `idempotency_conflict` повторно не отправляется. `409` с `idempotency_in_progress`, пока ответа ещё нет, не становится ошибкой инструмента: вызывающий повторяет тот же ключ.

Чужая версия и лишнее поле до модели не доходят. Слишком большое тело хаб не отправляет. Ответ больше `SERVICE_RESPONSE_BYTES` обрывается, в модель уходит короткая ошибка `payload_too_large`.

Сервис недоступен. Хаб не исполняет инструмент локально взамен. Шаг — ошибка, цикл модели продолжается, пока лок жив и не кончился `max_steps`.

`401` не повторяется. Это ошибка установки секрета, не повод слать тот же bearer ещё раз.

Потеря слота во время модели: `succeeded` не ставится. Если лок запуска ещё наш, `finish` со статусом `failed` и `error = slot_lost`. Если лок запуска тоже потерян, записей больше нет.

Heartbeat запуска вернул `false` во время HTTP: сокет обрывается, `finish` не вызывается.

## Безопасность

Разработка. Репозиторий сервиса не содержит токена, `DATABASE_URL` хаба и примеров ключей, похожих на настоящие. В нём `.env.example` с пустыми значениями. Ревью сверяет дифф с **I2**, **I3**, **I4**, **I7**, **I19** и с этим протоколом. Зависимость runtime вне `postgres`, `zod`, `pino` — стоп. Тесты ходят в `harness_files_test`. Боевые `harness` и `harness_files` тест не трогает.

Эксплуатация. Процесс сервиса — пользователь без входа в систему, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ReadWritePaths` только на `FILE_ROOT`. Каталоги хаба, `BLOB_ROOT` и домашний каталог ему не видны. Юнит не слушает `0.0.0.0`. Путь юнита выбирает установщик, спецификация домашний путь не назначает.

Секрета в файле манифеста нет. Хаб читает bearer из переменной окружения, имя которой записано в `auth.env`. Значение в манифест и в репозиторий не пишется. На стороне сервиса в базе и на диске хранится только SHA-256. Сравнение — SHA-256 предъявленного bearer против сохранённых 32 байт, `timingSafeEqual`. Ротация: новое значение переменной и новый хеш на сервисе, оба процесса перезапускаются, старый хеш удаляется. Журнал значение не видит.

В список `redact` хаба на время процесса входит секрет сервиса. Выпущенная способность добавляется в список на время хода, как в `05-files.md`.

Резервная копия сервиса — база `harness_files` вместе с `FILE_ROOT`. Восстановление одной половины без другой чинит человек. Автоматического сличения нет.

Лог сервиса: `run_id`, имя инструмента, `duration_ms`, код ошибки. Не аргументы, не `Authorization`, не текст файла.

Ворота CI репозитория `https://github.com/SanteraSan/harness-files` повторяют `07-git.md`, когда в нём появится код. Сейчас там только README. Имена проектов Sonar агент заранее не назначает. Bandit не добавляется, пока в репозитории нет Python. Появился `.py` — это отдельное решение, не этот пункт.

## Тесты

Команда сервиса — его `npm test` против `harness_files_test`. На хабе — `npm test` с фейковым HTTP сервиса, без живого `qwen`. Пропуск живого прогона без `HARNESS_LIVE_MODEL=1` остаётся нормой.

Злые входы:

- `../`, абсолютный путь, симлинк наружу, каталог `FILE_ROOT-evil`;
- симлинк `FILE_ROOT/out` на другой каталог, сегмент `.record-note`;
- имя `Bash` в манифесте и в allowlist не вызывает HTTP;
- неизвестное имя не вызывает HTTP;
- JSON инструмента в `content` не вызывает HTTP;
- лишнее поле ответа и поле `prompt_tokens` не попадают в историю модели и не меняют суммы;
- тело аргументов больше 32 КиБ не уходит в сокет;
- тот же ключ и тот же хеш не создают второй файл;
- тот же ключ и другой хеш дают `409` и не создают файл;
- обрыв сокета после записи: повтор возвращает первый результат;
- живой `started` без ответа не закрывается окончательным `409`: повтор того же ключа не пишет второй файл и, когда строка `done`, возвращает сохранённый ответ;
- фейковый токен в `text` отсутствует в `run_steps` и во втором запросе модели;
- heartbeat `false` во время вызова: `finish` не вызван;
- в теле вызова нет `chat_id`;
- очередь не импортирует клиент сервиса.

Два захвата идемпотентности в тесте сервиса — два соединения к `harness_files_test`. Мок модуля `postgres` это не заменяет.

## Критерии готовности

Воркер не импортирует `src/tools/read-file.ts`, `src/tools/list-dir.ts`, `src/tools/record-note.ts`. Юнит воркера не имеет `FILE_ROOT` в `ReadWritePaths`. Три имени по-прежнему видны модели локального агента, если они есть в allowlist и в манифесте. Запрет имён сильнее обоих списков. Очередь не импортирует клиент сервиса. `coder-cloud` после выполнения M3-P7 не получает список этих инструментов. До выполнения M3-P7 этот пункт поле `reasoning_effort` не добавляет.

## Пример. Jira

Отдельный репозиторий, когда человек его заведёт. Контракт тот же, `harness.tool.v1`. Хаб берёт имя из локального манифеста и проекта Jira не знает. Эффект `write`. Токен Jira только в окружении этого сервиса. В модель, в журнал и в репозиторий сервиса он не входит.

Модель передаёт короткие поля: проект, заголовок, текст. Сервис создаёт задачу своим клиентом. Обратно уходит строка вида «создана задача PROJ-1». Тело задачи и сырой ответ Jira в контекст модели не копируются. Ключ — `Idempotency-Key` со значением `<run_id>:<tool_call_id>`. Тот же ключ и тот же хеш возвращают первую строку. Тот же ключ и другой хеш дают `409`. Чужая версия задачу не создаёт. В ответе есть `duration_ms`. В `run_steps` хаб его не пишет, пока колонки нет. Полей токенов в ответе нет. Экран Jira хаб не рисует.

Этот пример кодом HARNESS не реализуется.

## Пример. Длинный текст

Отдельный репозиторий, когда человек его заведёт. Контракт тот же. Эффект в манифесте — `read` или `write` по смыслу вызова. Сервис может вызвать свою модель. Хабу он токены той модели не объявляет. `prompt_tokens`, `completion_tokens` и `cost_usd` в ответе — отказ разбора.

В модель хаба входит короткий итог не длиннее 8000 кодпоинтов. Если текст длиннее, сервис сдаёт его хабу байтами по `05-files.md` и возвращает id в `blobs`. Модель видит идентификатор в итоге, не тело. Для `write` хранится ключ и хеш. Тот же ключ и тот же хеш вторую генерацию не начинают.

Этот пример кодом HARNESS не реализуется.
