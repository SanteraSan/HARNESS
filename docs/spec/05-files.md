# 05. Файлы

## Назначение

Клиент передаёт файл хабу. Хаб хранит байты у себя и отдаёт сервису одноразовую способность, не тело в контекст модели. Сервис возвращает короткий итог или новый файл. Дальше человек читает результат тем же id своим bearer.

`BLOB_ROOT` — каталог хаба, отдельный от `FILE_ROOT`. Байты лежат на диске. Метаданные — в Postgres хаба. В контекст модели входят id и размер строкой `file <uuid> <bytes>`. В сервис способность входит только если манифест инструмента говорит `accepts_blobs: true`.

У `read_file`, `list_dir` и `record_note` `accepts_blobs` равен `false`. Они работают с `FILE_ROOT` внутри файлового сервиса и способность не получают. `read_file` не копирует рабочий файл в blob. Длинный текст режется флагом `truncated`. В модель после хаба входит не больше 8000 кодпоинтов. Потолок чтения сервиса остаётся 64 КиБ UTF-8.

## Что в пункт не входит

Нет общего хранилища с картинками M4. Нет выдачи файла через Telegram. Нет имени пользователя в пути. Нет постоянного URL с секретом в query. Нет второго корня у файлового сервиса: `BLOB_ROOT` он не монтирует.

## Правила ядра

**I19** для `BLOB_ROOT` исполняет процесс `api`: `realpath`, префикс с разделителем, отказ на `..`, абсолютный путь снаружи, симлинк наружу и каталог `BLOB_ROOT-evil`. **I19** для `FILE_ROOT` после выноса исполняет файловый сервис. Воркер оба корня не открывает.

**I4** сохраняется. Сырой токен способности добавляется в список `redact` на время хода, до журнала и до следующего сообщения модели. В `request_excerpt` попадает имя инструмента и хеш канонического тела, не токен.

**I7** сохраняется. Способность вставляется и ingest принимается только пока лок запуска наш. Потеря лока не ставит `succeeded`.

**I1** сохраняется. Очередь клиент файлов не импортирует. Байты читает процесс `api`.

Новые таблицы и колонка — миграции `010_blobs.sql` и `011_step_duration.sql`. Старые файлы миграций не переписываются. `runs.payload` уже jsonb: отдельная колонка под id файлов не добавляется.

## Технологии

Идентификатор файла — `crypto.randomUUID()`. Имя на диске — этот uuid, один сегмент, нижний регистр. Каталог проверяется тем же правилом, что `security.mdc`.

Временный файл пишется в `BLOB_ROOT/.tmp/<uuid>` и переименовывается на окончательное имя только после полной проверки длины и суммы. `.tmp` после `realpath` остаётся внутри `BLOB_ROOT`. Каталог `.tmp` не отдаётся никаким маршрутом.

Способность — 32 байта `crypto.randomBytes`. В заголовок она кодируется base64url без `=`. В базе хранится SHA-256 этих 32 байт. Сырой токен в журнал не пишется.

Срок способности — 60 с от `now()` Postgres. Одна успешная выдача. Привязка к `service_id`, `run_id` и `tool_call_id`. Секрет в URL не ставится: выдача и предъявление идут заголовком `X-Capability`.

Потолок по умолчанию — 32 МиБ. `BLOB_MAX_BYTES` выше 128 МиБ не даёт процессу стартовать. Срок хранения файла — 7 суток от `now()`.

`media_type` хаб ставит сам: `application/octet-stream`. Чужой тип не принимается, путём не становится и HTML не становится.

Диск и Postgres — локальные. Отдельное объектное хранилище не вводится.

## Протокол способности

Хаб выпускает способность только пока держит лок этого запуска, только для инструмента с `accepts_blobs: true` и только на blob этого `tenant_id`, который указан в постановке или принят ingest этого же запуска. На пару blob и `tool_call_id` выпускается не больше одной способности. На один вызов — не больше 8.

Клиентские маршруты загрузки и метаданных описаны в `04-client-protocol.md`. Здесь — служебные.

Сервис забирает байты так:

`GET /v1/blobs/:id/content`

- `Authorization: Bearer <долгий секрет сервиса>`;
- `X-Capability: <base64url 32 байт без «=»>`;
- клиентского bearer нет.

Оба должны сойтись со строкой: сервис из bearer, запуск, файл, `tool_call_id` той способности, `used_at is null`, `expires_at > now()`. Отметка `used_at = now()` ставится одним `UPDATE` в короткой транзакции до потока байтов. Транзакция коммитится до чтения файла. Вторая выдача — `401` и `reason: "capability_used"`. Просрочка — `401` и `reason: "capability_expired"`. Чужой сервис, чужой запуск, неверный токен и неверный id — `404` и `reason: "not_found"`. Так чужой id не подтверждается.

Различать `capability_used` и `capability_expired` можно только когда хеш токена найден и `service_id` с `run_id` совпали. Иначе `404`.

Клиентский bearer вместе со способностью — `400` и `invalid_request`. Bearer сервиса без `X-Capability` — `401` и `unauthorized`: id файлом не подтверждается.

Способность уходит сервису на вызове инструмента заголовком `X-Capability`, не полем JSON.

Значение заголовка — один base64url без `=`, ровно 32 байта токена. В пример значение не подставляется. Повтор заголовка — по одной способности. В каноническое тело хеша идемпотентности заголовки не входят. У трёх файловых инструментов заголовка нет, потому что `accepts_blobs` ложен.

Новый файл от сервиса:

`POST /v1/blobs/ingest`

- долгий bearer сервиса, не клиентский;
- `Content-Type: application/octet-stream` без параметров;
- `Content-Length` обязателен;
- `Idempotency-Key` — quoted-string `<run_id>:<tool_call_id>`, как в `01-services.md`;
- `X-Run-Id` и `X-Tool-Call-Id` совпадают с этим ключом;
- тело не больше потолка;
- лок запуска ещё держится: `status = 'running'` и `locked_until > now()`.

Сервис не присылает `worker_id`. Поле в контракт `v1` не добавляется. Проверка лока — живая аренда этой строки `runs`. Чужой или просроченный лок — `409` и `reason: "run_lock_lost"`. Временный файл удаляется.

Ответ `201`:

```json
{ "id": "00000000-0000-4000-8000-0000000000bb", "bytes": 4, "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef" }
```

Тот же ключ и тот же SHA-256 байтов — `200` и первый id. Тот же ключ и другой хеш — `409` и `idempotency_conflict`, второго файла нет.

Id сервис возвращает в массиве `blobs` ответа инструмента. Хаб проверяет, что каждый id создан этим `run_id`. Чужой id — отказ разбора ответа, модели он не отдаётся, шаг `tool_result` с `error: "invalid_body"`.

Дальше человек читает тот же id клиентским bearer. Сервис свой экран от хаба не получает.

## Данные

Миграция `migrations/010_blobs.sql`, файл этим документом не создаётся.

`blobs`:

- `id uuid primary key`;
- `tenant_id text not null`;
- `sha256 bytea not null`, длина 32;
- `byte_size bigint not null`, от 0 до потолка конфига;
- `media_type text not null`, только `application/octet-stream`;
- `created_at timestamptz not null default now()`;
- `expires_at timestamptz not null`;
- `idempotency_scope text`, значения `client` и `ingest`, вместе с ключом;
- `idempotency_key text`;
- `body_sha256 bytea`, длина 32, когда ключ есть;
- уникальность `(tenant_id, idempotency_scope, idempotency_key)`, где ключ не null.

Ключ клиента и ключ `<run_id>:<tool_call_id>` лежат в разных `idempotency_scope`. Одинаковый текст ключа в двух областях не сталкивается.

`blob_capabilities`:

- `id uuid primary key`;
- `blob_id uuid not null references blobs (id)`;
- `token_sha256 bytea not null`, длина 32, уникальный;
- `service_id text not null`;
- `run_id uuid not null`;
- `tool_call_id text not null`;
- `expires_at timestamptz not null`;
- `used_at timestamptz`;
- уникальность `(blob_id, run_id, tool_call_id)`.

`run_steps.duration_ms` — миграция `migrations/011_step_duration.sql`: `integer`, null или не меньше нуля. Старые шаги остаются null. Писать колонку можно только в `UPDATE` шага, у которого лок запуска ещё наш, тем же условием, что сейчас дописывает `cost_usd`.

Удаление просроченных файлов делает процесс воркера в том же цикле, где он уже вызывает `reapExpired`. Отдельный крон не заводится. За проход не больше 20 строк: выбрать id с `expires_at < now()`, удалить строки, закоммитить, затем удалить файлы. `unlink` транзакцию не держит. Путь файла после `realpath` обязан лежать в `BLOB_ROOT`. Файл без строки удаляется только если имя — один uuid и путь внутри корня, не больше 20 за проход. Строка без файла на чтении даёт `404`. Временные файлы в `.tmp` старше одного часа удаляются тем же проходом, не больше 20, только внутри корня. Час — запас над `requestTimeout` в 30 с, не второй срок хранения.

## Порядок относительно захвата

Клиент загружает байты до постановки либо не загружает их. Запись байтов идёт вне транзакции метаданных: сначала временный файл, затем короткая вставка строки, затем переименование. Ошибка вставки удаляет временный файл. Постановка коммитится без держания байтов: в ней только проверка id.

Захват запуска коммитится до модели. Слот отпускается до HTTP сервиса. Способность вставляется коротким оператором уже во время хода, после захвата и после отпускания слота, и коммитится до `fetch` сервиса. Поток байтов по `GET …/content` транзакцию не держит: `used_at` уже закоммичен.

Ingest сервиса проверяет живой лок отдельным коротким оператором и не продлевает аренду. Продлевает её heartbeat воркера.

## Отказы

Таймаут чтения способности — ошибка инструмента, запуск жив. Новая способность на тот же blob и тот же `tool_call_id` сама не выпускается. Сервис, который не успел, получает ошибку. Повтор всего запуска — новый `tool_call_id` и поэтому новая способность, если лок нового хода наш.

Потеря лока до ingest — `409` `run_lock_lost`. Байты временного файла удаляются. Повтор того же ключа и того же хеша после успешного ingest возвращает первый id, даже если лок к повтору уже истекает: сохранённый id принадлежит тому же ключу. Повтор с другим хешем файл не создаёт.

Тело больше потолка не сохраняется, даже если `Content-Length` меньше факта. Несовпадение длины — `400`, файла нет.

Чужой URL вместо id в `blobs` ответа — не uuid, отказ разбора, модели не отдаётся.

`accepts_blobs: false` при присланном `X-Capability` от хаба не случается: хаб заголовок не ставит. Если сервис сам просит способность для такого инструмента, хаб её не выпускает.

## Безопасность

Разработка. Тесты пути живут рядом с хранилищем и используют временный каталог. Боевой `BLOB_ROOT` тест не трогает. В фикстуре нет настоящего секрета. Ревью смотрит, что способность не попадает в `request_excerpt` и в pino.

Эксплуатация. `BLOB_ROOT` есть только у процесса `api` в `ReadWritePaths`. Воркер и файловый сервис каталог не монтируют на запись. Режим каталога не даёт читать его всем пользователям машины. Юнит `api`: `NoNewPrivileges=yes`, `ProtectSystem=strict`.

Копия: база хаба и `BLOB_ROOT` снимаются вместе. Иначе клиент видит id без байтов.

Ротация долгого секрета сервиса гасит уже выпущенные способности на следующем запросе, потому что bearer сервиса тоже проверяется. Клиентские хеши при этом не крутятся.

Лог: id файла, `run_id`, код отказа. Не байты, не `X-Capability`, не сырой SHA способности. Клиенту свой `sha256` в ответе загрузки отдаётся: это его файл.

## Тесты

- путь `../`, абсолютный, симлинк наружу и префикс `BLOB_ROOT-evil` не читаются;
- имя файла не берётся из заголовка клиента;
- второй redeem — `401` и `capability_used`;
- просрочка при верном токене, сервисе и запуске — `401` и `capability_expired`;
- чужой `service_id`, чужой `run_id` и неверный токен — `404` и `not_found`;
- сырого токена нет в `run_steps` и в записи pino теста;
- файл 32 МиБ плюс 1 байт не сохраняется;
- конфиг 129 МиБ не даёт процессу стартовать;
- тот же ключ ingest и другой хеш — `409` и один файл;
- тот же ключ ingest и тот же хеш возвращают первый id;
- потеря лока до ingest — `409` `run_lock_lost`, файла нет;
- байты файла отсутствуют в сообщении, которое тестовая модель получила следующим ходом;
- в модель входят id и размер, не путь;
- `chat_id` в теле вызова сервиса отсутствует;
- инструмент с `accepts_blobs: false` не получает `X-Capability`;
- вторая способность на ту же пару blob и `tool_call_id` не вставляется;
- удаление просрочки снимает не больше 20 строк за проход и не удаляет файл вне корня.

Тесты базы идут в `harness_test`. `BLOB_ROOT` теста — временный каталог внутри каталога теста.

## Критерии готовности

Модель не получает тело файла. Сервис без `accepts_blobs` не получает способность. Одноразовая способность живёт 60 с и привязана к сервису, запуску и `tool_call_id`. `FILE_ROOT` и `BLOB_ROOT` не совпадают и не вложены друг в друга: проверка корней на старте отвергает совпадение после `realpath`. **I19** соблюдён на том корне, который процесс открывает. Воркер ни один из корней не открывает.
