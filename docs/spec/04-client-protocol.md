# 04. Протокол клиента

## Назначение

Клиент говорит с хабом развитием текущего HTTP. Один сценарий: отправил сообщение или файл, получил запуск, прочитал итог. Итог по-прежнему читается `GET /v1/runs/:id`.

Новые маршруты — только файлы и приём файла от сервиса. Контракт хаб↔сервис остаётся `harness.tool.v1` и в эти маршруты не превращается. Клиент сервис напрямую не вызывает.

Telegram остаётся процессом поставки. Рядом — критерии, когда его позже можно сделать клиентом того же HTTP. Сейчас он не выносится.

`source` новых клиентов остаётся `api`. Новое значение check-ограничения `source` не добавляется.

## Что в пункт не входит

Нет фреймворка оболочки. Нет голосового движка. Нет пользователей, нет OAuth, нет refresh-токенов. Нет выноса бота. Нет CORS. Нет имени файла в заголовке и в URL. Нет секрета в query.

Оболочки и голос подчиняются этому протоколу, требования к ним — в `08-shells-and-voice.md`. Байты и способности — в `05-files.md`.

## Правила ядра

Сохраняются **I5**, **I6**, **I9**, **I14**, **I20**. Пара `(agent_id, idempotency_key)` возвращает ту же строку. Живой чат возвращает живой запуск. `tenant_id` остаётся `local`. Telegram модель не вызывает.

**I11** сохраняется: `source` принимает `api` и `telegram`. Клиент HTTP по-прежнему пишет `api`.

Меняется только тело постановки: у `POST /v1/runs` появляется необязательное поле `blob_ids`. Неизвестные прочие поля постановки по-прежнему отбрасываются. Это исключение не переносится на контракт сервиса и не переносится на маршруты файлов.

**I15** сохраняется. Новый npm-пакет для клиента не добавляется. Тот же Hono и `node:http`.

Лимит JSON 32 КиБ сохраняется. Загрузка файла идёт отдельным маршрутом со своим потолком, потому что общий лимит файл не перевозит. `Content-Type` сверяется с телом. Файл, объявленный как JSON на `POST /v1/runs`, постановкой не принимается.

## Технологии

Тот же сервер. `API_LISTEN_HOST` остаётся `127.0.0.1`. Порт остаётся `8787`. `requestTimeout` 30 с и `headersTimeout` 10 с остаются и для JSON, и для загрузки: отдельный более длинный таймаут не вводится. Незавершённая загрузка файл не оставляет.

Заголовок `X-Content-Type-Options: nosniff` остаётся на каждом ответе, включая байты.

Сейчас секрет один: `HARNESS_API_TOKEN`, сравнение сырых буферов равной длины через `timingSafeEqual`. Расширение — несколько именованных токенов. Файл хешей задаёт `CLIENT_TOKEN_HASHES`, режим не слабее `0600` (группа и прочие не читают). Иной режим — процесс выходит до `listen`. Элемент строки: `name`, один пробел, 64 hex SHA-256 в нижнем регистре. `name` совпадает с `^[a-z][a-z0-9_-]{0,63}$`. Пустых строк и комментариев нет. Повтор имени — конфигурация недействительна.

Сырого токена в файле нет. Проверка: SHA-256 предъявленного bearer, затем `timingSafeEqual` с каждой сохранённой суммой. Сравнение идёт по всем строкам, без выхода на первом совпадении. Отзыв удаляет одну строку. Остальные хеши не меняются. `SIGHUP` файл не перечитывает.

Пока `HARNESS_API_TOKEN` не пуст, процесс на старте считает его SHA-256 в память под именем `legacy` и дальше сравнивает только хеш. Пустое значение по-прежнему не открывает API. Имя `legacy` в файле вместе с непустым токеном окружения — конфигурация недействительна. Значение в лог не пишется. Сырой токен остаётся в списке `redact`, как сейчас.

Учётных записей людей нет. Именованный токен — не пользователь.

`startHttpServer` сейчас режет любое тело на 32 КиБ до маршрута. Для `POST /v1/blobs` и `POST /v1/blobs/ingest` ветка потолка выбирается раньше этого лимита и только когда путь ровно этот, метод `POST`, а `Content-Type` — `application/octet-stream` без параметров. Любой другой путь сохраняет лимит 32 КиБ. Query-строка на новых маршрутах — `400` и `reason: "invalid_request"`.

## Протокол

Уже существующие маршруты сохраняют коды и поля.

### `GET /health`

Без токена. `200` и `{ "ok": true }`. Это единственный маршрут без bearer.

### `POST /v1/runs`

Заголовки: `Authorization: Bearer`, `Content-Type: application/json` или с единственным параметром `charset=utf-8`.

Прежние поля и необязательный `blob_ids`: массив uuid, длина 0..8. Пустой массив в `payload` не пишется. Неизвестный другой ключ по-прежнему не мешает постановке. Повтор uuid в массиве — `400` и `reason: "invalid_body"`. Неизвестный id, чужой `tenant_id`, просроченный файл — тот же `400` и `invalid_body`, без признака, какой из случаев сработал.

```json
{
  "agent_slug": "clerk",
  "idempotency_key": "client-1",
  "message": "посмотри файл",
  "chat_id": "100",
  "blob_ids": ["00000000-0000-4000-8000-0000000000aa"]
}
```

`chat_id` — десятичная строка канонического int8 либо `null`. JSON-число отвергается. `Number(chat_id)` не вызывается. Разбор идёт через `bigint`, в драйвер уходит строка.

В `payload` сохраняются `message` и, когда массив не пуст, `blob_ids`. Раннер добавляет к пользовательскому тексту строки после пустой строки, по одной на ещё живой файл:

```text
file 00000000-0000-4000-8000-0000000000aa 12
```

Uuid в нижнем регистре, размер — десятичное число байтов без ведущих нулей. Пути на диске нет. Байтов файла нет. Порядок строк — порядок `blob_ids`. Если к моменту хода строка файла уже просрочена или удалена, эта строка в текст не входит и запуск из-за этого не становится `failed`.

Если текст сообщения плюс эти строки не укладывается в 8000 единиц UTF-16, постановка отвечает `400` и `reason: "invalid_body"`. Сообщение человека молча не режется.

Ответы постановки, как сейчас:

```json
{ "id": "00000000-0000-4000-8000-000000000010", "reason": "created", "status": "queued" }
```

`201` и `created`. `200` и `replay` — тот же id. `409` и `dialog_busy` — id живого запуска и его `status`. Неизвестный `agent_slug` — `404` и `unknown_agent`.

### `GET /v1/runs/:id`

Как сейчас: `{ "run", "steps" }`. `chat_id` в JSON — строка или `null`. В теле нет `Authorization`, нет `DATABASE_URL`, нет байтов файла и нет сырого `X-Capability`. Не uuid — `400` и `invalid_id`. Чужой или отсутствующий id при верном uuid — `404` и `not_found`. Фильтр `tenant_id = local` остаётся.

### `POST /v1/blobs`

Тело не JSON.

- `Authorization: Bearer` клиентского токена. Bearer сервиса на этом маршруте — `401`.
- `Content-Type: application/octet-stream` без параметров.
- `Content-Length` обязателен, одно поле. Повтор заголовка — `400` и `invalid_request`.
- Необязательный `Idempotency-Key`: видимый ASCII `0x21`…`0x7E`, длина 1..256, ровно один заголовок. Это не quoted-string контракта сервиса. Кавычки, пробел и двоеточие здесь обычные символы, если они внутри диапазона.

`201` и тело:

```json
{ "id": "00000000-0000-4000-8000-0000000000aa", "bytes": 12, "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef" }
```

`sha256` — 64 hex в нижнем регистре, сумма байтов тела. Тот же ключ и тот же SHA-256 — `200` и тот же `id`, `bytes`, `sha256`. Тот же ключ и другие байты — `409` и `{ "reason": "idempotency_conflict" }`. Больше потолка — `413` и `payload_too_large`, файла на диске нет. Нет `Content-Length`, длина не сошлась с фактическим числом байтов, чужой `Content-Type` — `400` и `invalid_body`, файла нет. Имя файла заголовком не принимается и путём не становится.

Потолок по умолчанию — `BLOB_DEFAULT_BYTES` (32 МиБ). Конфиг `BLOB_MAX_BYTES` не может поднять его выше `BLOB_ABSOLUTE_MAX_BYTES` (128 МиБ): процесс не стартует. Счётчик байтов режет тело и тогда, когда `Content-Length` меньше факта.

### `GET /v1/blobs/:id`

Метаданные, без байтов. Клиентский bearer. Сервисный bearer — `404` и `not_found`.

```json
{
  "id": "00000000-0000-4000-8000-0000000000aa",
  "bytes": 12,
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "media_type": "application/octet-stream",
  "expires_at": "2026-11-18T12:00:00.000Z"
}
```

Нет пути, нет `tenant_id`. Просроченный, чужой и неизвестный id — `404` и `not_found`.

### `GET /v1/blobs/:id/content`

Байты. Два разных входа, сразу оба — `400` и `invalid_request`.

Клиентский bearer без `X-Capability`: тело — байты, `Content-Type: application/octet-stream`, `Content-Length` равен размеру, `nosniff`. Имени файла в `Content-Disposition` нет.

Служебный вход — долгий bearer сервиса и заголовок `X-Capability`. Его правила — в `05-files.md`. Клиентский токен способность не заменяет.

### `POST /v1/blobs/ingest`

Маршрут сервиса, не клиента. Клиентский bearer — `401`. Правила тела, ключа и лока — в `05-files.md`.

Все ответы несут `nosniff`. Тело ошибки — `{ "reason": "<код>" }` без стека и без `DATABASE_URL`. Новые `reason` этого пункта: `idempotency_conflict`. Коды `capability_used`, `capability_expired` и `run_lock_lost` задаёт `05-files.md`. Уже существующие коды сохраняются: `unauthorized`, `invalid_body`, `invalid_id`, `invalid_request`, `payload_too_large`, `unknown_agent`, `not_found`, `internal_error`.

`Access-Control-Allow-Origin` хаб не ставит. Произвольный `Origin` не отражается.

## Данные и порядок

Постановка по-прежнему одна транзакция: блокировка ключа идемпотентности, затем живой `chat_id`, затем `insert`. Файл к этому моменту уже лежит в `BLOB_ROOT`, либо массива нет. Загрузка клиента до постановки `runs.attempt` не сверяет: запуска ещё нет. Поколение аренды проверяет только ingest живого запуска, правила в `05-files.md`. В транзакции постановки проверяются id, срок и `tenant_id`. Байты в транзакцию не читаются. Захват воркера идёт после ответа HTTP клиенту.

`chat_id` в запрос сервиса не копируется.

Идемпотентность загрузки хранится 72 часа на паре ключа и SHA-256 байтов. Позже тот же ключ может создать новый id. Это тот же `IDEMPOTENCY_TTL`, что у записи инструмента. Срок файла — 7 суток и от ключа не зависит.

Строки хешей клиентов в базе хаба не лежат. Копия базы без файла хешей оставляет API закрытым, пока оператор не положит хеши заново. Непустой `HARNESS_API_TOKEN` в окружении процесса по-прежнему открывает доступ под именем `legacy`.

## Отказы

Нет bearer — `401`, кроме `GET /health`. Чужой токен — `401`. Отозванный хеш — `401`, остальные токены живы. Повтор ключа запуска — тот же id. Живой чат — `409` и id живого. Тело JSON больше 32 КиБ — `413` на постановке, даже если `Content-Type` объявлен как файл. Файл на маршрут постановки не принимается.

Оба заголовка, клиентский bearer и `X-Capability`, на чтении байтов — `400`.

Обрыв загрузки по `requestTimeout` файл не оставляет. Клиент видит обрыв или `408` самого Node на `requestTimeout`. Отдельный JSON `reason` для этого таймаута не вводится: ответ может не успеть. Частичный файл удаляется.

Повтор `Idempotency-Key` загрузки с другими байтами второй файл не создаёт.

## Безопасность

Разработка. Секрет в репозиторий и в фикстуру, похожую на боевой ключ, не кладётся. В тестах строка `test-secret-value`. Оболочка в этот репозиторий не добавляется. Ревью смотрит, что API не импортирует `ChatModel` и клиент сервиса. `eslint-disable` без причины в отчёте не оставляется.

Эксплуатация. Файл хешей вне каталога репозитория. Ротация одного имени меняет одну строку хеша, не переписывает секреты других имён. Журнал HTTP хранит `run_id` и `reason`, не заголовок `Authorization`. Туннель, если он есть, заканчивается на `127.0.0.1:8787` и bearer не заменяет. Требования к туннелю — в `06-phone.md`.

Слушать `0.0.0.0` нельзя. Менять `API_LISTEN_HOST` ради клиента нельзя.

## Тесты

- без токена `POST /v1/runs` даёт `401`, `GET /health` даёт `200`;
- второй именованный токен работает, удаление его хеша даёт `401`, первый жив;
- сравнение не возвращается на первом совпадении: тест с двумя хешами видит оба вызова равной длины;
- пустой `HARNESS_API_TOKEN` и пустой файл хешей не открывают `POST`;
- повтор `idempotency_key` постановки возвращает тот же запуск;
- живой `chat_id` даёт `409` и id живого;
- `blob_ids` длиннее 8 отвергается, повтор uuid отвергается;
- неизвестный `blob_ids` даёт `400`, и в теле ответа нет признака «существует, но чужой»;
- загрузка больше потолка даёт `413`, и файла на диске нет;
- `Content-Length` меньше фактического тела даёт `400`, файла нет;
- тот же ключ загрузки и другие байты — `409` и один id;
- тот же ключ и те же байты — `200` и тот же id;
- `chat_id` длиннее точного целого и JSON-число не проходят через `Number`;
- в `GET /v1/runs/:id` нет `Authorization` и нет байтов файла;
- `POST /v1/runs` с `Content-Type: application/octet-stream` не создаёт запуск;
- query на `POST /v1/blobs` даёт `400`;
- API-модуль не импортирует `ChatModel`.

## Критерии готовности

Старые маршруты зелёные и сохраняют прежние `reason`. Новые файловые маршруты требуют bearer. Пользователей и OAuth нет. Бот на месте и файлы по-прежнему не принимает. Технология оболочки не названа как выбранная. `source` нового клиента — `api`.

## Когда Telegram можно вынести

Вынос сейчас не делается. Он станет отдельной работой только когда одновременно верно всё:

- боту достаточно `POST /v1/runs`, `GET /v1/runs/:id` и `GET /health`;
- каталог `src/telegram` больше не нужен очереди, раннеру и модели, а сам не импортирует их;
- токен бота живёт только в окружении этого клиента;
- буфер занятого чата и отметка доставки либо выражены ответами HTTP, либо сознательно оставлены внутри клиента;
- файлы и голос боту по-прежнему не обещаны.

До этого бот в поставке. Файл, стикер, голос и пустой текст по-прежнему не создают запуск: ответ, что в этом срезе принимается только текст. Приём файла ботом этот пункт не добавляет. Копирования истории сообщений нет.

Сейчас процесс `telegram` ставит запуск и потом читает статус. Это **I14**. Вынос, который заставляет бота звать модель, запрещён и после критериев.
