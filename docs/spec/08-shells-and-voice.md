# 08. Оболочки и голос

## Назначение

Оболочка — клиент хаба. Веб, десктоп и телефон показывают один сценарий: человек отправил сообщение или файл, оболочка получила запуск, оболочка прочитала итог. Голос в этом сценарии становится текстом и уходит той же постановкой.

Протокол к хабу — `04-client-protocol.md`. Другого API оболочка не получает. Туннель, если хаб не на лупбэке этой машины, — требования `06-phone.md`.

Фреймворк оболочки и движок распознавания этот файл не выбирает. Пакета кода в репозитории HARNESS он не открывает.

## Что в пункт не входит

Нет выбора React, Vue, Svelte, Swift, Kotlin и любого другого UI-стека. Нет выбора движка распознавания. Нет решения, на устройстве распознавание или снаружи. Нет Electron, IPC и `executeJavaScript`: к этому репозиторию они не относятся и этим пунктом не выбираются. Нет пользователей и OAuth. Нет своего протокола поверх HTTP. Нет прямого вызова сервиса, Postgres, `FILE_ROOT` и `BLOB_ROOT`.

Вынос Telegram сюда не входит. Критерии выноса — в `04-client-protocol.md`. Пока они не выполнены, бот остаётся процессом поставки и оболочкой по этому файлу не становится.

## Правила ядра

Оболочка правила очереди не меняет. Она клиент. **I5** и **I6** остаются на хабе: повтор ключа возвращает тот же запуск, живой чат возвращает `409`. Оболочка второй запуск «для надёжности» не создаёт, если ответ был `replay` или `dialog_busy`.

**I14** не меняется. Telegram модель не вызывает, и оболочка модель тоже не вызывает. Модель вызывает только воркер хаба.

**I20** распространяется на журнал оболочки: bearer, токен бота и ключ шлюза туда не пишутся. Сырой ответ шлюза оболочка не получает и не хранит. Его видит воркер.

**I2** не переносится в оболочку как право исполнять JSON из текста модели. Текст модели и текст инструмента показываются как простой текст.

Лимиты хаба оболочка не поднимает. `message` — 8000 единиц UTF-16. Тело JSON постановки — 32 КиБ. Файл — потолок `BLOB_MAX_BYTES`, по умолчанию 32 МиБ, не выше 128 МиБ.

## Технологии

Стек UI не выбирается. Движок распознавания не выбирается. Хранилище секрета — хранилище платформы, которую выберут позже, а не файл в дереве проекта. На телефоне это хранилище секретов ОС, как в `06-phone.md`.

Транспорт до хаба на другой машине — туннель из пункта 6. Проверка TLS на клиенте включена. `rejectUnauthorized: false` и `NODE_TLS_REJECT_UNAUTHORIZED=0` запрещены.

Оболочка не слушает `0.0.0.0`. Если ей вообще нужен порт, он не публикует хаб, базу и сервис.

Новый npm-пакет в репозиторий HARNESS этим пунктом не добавляется.

## Протокол

Оболочка вызывает только маршруты хаба из пункта 4. Сервис `POST /v1/tools/{name}` она не вызывает. `POST /v1/blobs/ingest` она не вызывает.

Постановка:

```http
POST /v1/runs HTTP/1.1
Host: 127.0.0.1:8787
Authorization: Bearer <токен из хранилища платформы>
Content-Type: application/json; charset=utf-8
```

```json
{
  "agent_slug": "clerk",
  "idempotency_key": "shell-1",
  "message": "текст человека или текст расшифровки",
  "chat_id": "42",
  "blob_ids": ["00000000-0000-4000-8000-0000000000aa"]
}
```

`blob_ids` опускается, когда файлов нет. `chat_id` — строка или поле опущено. Bearer в URL нет.

Ответ `201` `created` и `200` `replay` показывают один и тот же id. `409` `dialog_busy` показывает id живого запуска и не шлёт вторую постановку с новым ключом, если человек не просил новое сообщение.

Итог:

```http
GET /v1/runs/00000000-0000-4000-8000-000000000010 HTTP/1.1
Authorization: Bearer <токен из хранилища платформы>
```

Оболочка показывает `status`, `final_text` и `error` как простой текст. Шаги показывает как простой текст. HTML из этих полей не собирается. Байтов файла в этом ответе нет.

Файл:

```http
POST /v1/blobs HTTP/1.1
Authorization: Bearer <токен из хранилища платформы>
Content-Type: application/octet-stream
Content-Length: 12
```

Тело — байты. Имени файла хаб не принимает. Ответ `201` даёт `id`, `bytes`, `sha256`. Этот id оболочка кладёт в `blob_ids`. В `message` она кладёт текст человека, не байты. Повтор той же загрузки с тем же `Idempotency-Key` и теми же байтами использует вернувшийся id и второй файл не рисует как новый.

Чтение своего файла — `GET /v1/blobs/:id/content` с клиентским bearer и без `X-Capability`. Метаданные — `GET /v1/blobs/:id`. Оба заголовка сразу оболочка не шлёт.

`GET /health` без токена годится как проверка пути. `200` и `{ "ok": true }` не считаются входом в API.

Голос. Микрофон выключен, пока человек сам не начал ввод. В запуск уходит текст расшифровки тем же `POST /v1/runs`, поле `message`, тот же предел 8000. Аудио не является полем постановки, не является аргументом инструмента и не подмешивается в контекст модели как байты. Отдельного маршрута для звука нет. Добавлять его нельзя: этого маршрута в хабе нет.

Если будущий движок отправляет звук наружу, это отдельное решение. Этот файл его не принимает. Bearer в звук не кладётся.

Оболочка не поднимает потолки. Текст длиннее 8000 она не отправляет: человек видит отказ до HTTP либо хаб отвечает `400` `invalid_body`. Файл толще потолка хаб отвечает `413`, оболочка частично принятый id не придумывает.

## Данные и порядок

Оболочка не пишет в Postgres. Порядок на хабе тот же: загрузка файла коммитит метаданные до постановки, постановка — одна транзакция, захват воркера — после ответа клиенту. Оболочка не ждёт модель внутри своего HTTP-запроса постановки. Она хранит id запуска и читает `GET`, пока статус не конечный либо человек не ушёл.

Ключ идемпотентности оболочка выбирает на одно действие человека. Повтор отправки того же действия использует тот же ключ. Новое действие человека получает новый ключ. `Date.now` и `Math.random` для ключа, который должен переживать повтор, не используются: ключ действия хранится вместе с черновиком. Формат — видимый ASCII 1..256, как у постановки хаба.

Секрет оболочка держит в хранилище платформы. В дерево проекта, в скриншот журнала и в текст `message` он не копируется. На телефоне хранилище — хранилище ОС. Репозиторий оболочки, когда он появится, содержит `.env.example` с пустыми значениями, если ему нужен пример имён, и не содержит сырой токен.

Обрыв пути не ставят на хабе в `succeeded`. Оболочка по обрыву `GET` не рисует успех. Она повторяет `GET` с тем же id.

## Отказы

`401` — нет или отозван bearer. Оболочка не подставляет другой токен того же хранилища молча, если человек выбрал конкретное имя. Нет ни одного токена — она не шлёт запрос с пустым `Authorization`.

`409` `dialog_busy` — показать id живого, не создавать второй запуск.

`413` — файл не принят. Локальный черновик можно оставить у человека. На диске хаба файла нет.

`400` `invalid_body` — показать короткую причину по полю `reason`. Тело исключения хаба оболочка не получает: его нет в ответе.

Отказ сети до постановки — запуска нет. Повтор с тем же ключом после восстановления пути безопасен.

Текст модели с угловыми скобками, ссылками и управляющими символами остаётся текстом. Оболочка не исполняет его как HTML, скрипт, `eval` или `new Function`.

## Безопасность

Разработка. Репозиторий оболочки не появляется внутри HARNESS этим пунктом. Секрет в фикстуру HARNESS не кладётся. Ревью будущего репозитория оболочки отвергает bearer в URL, в query, в репозитории, в журнале и в тексте, который уходит модели. Ревью отвергает прямой URL сервиса и строку подключения к Postgres.

Эксплуатация. Журнал оболочки, какой стек у него ни будет выбран позже, не хранит тело файла, заголовок `Authorization` и сырой ответ шлюза модели. Допустимы время, id запуска и `reason`.

Микрофон не включается фоном и не включается на старте экрана. Включение — действие человека на этот ввод. Конец ввода микрофон выключает.

Файл с сырым токеном в дереве проекта не хранится. Копия экрана и журнал отладки секрет не содержат.

Оболочка не слушает все интерфейсы. Путь не через лупбэк идёт туннелем пункта 6, с взаимной аутентификацией и шифрованием. Туннель bearer не заменяет.

Пользователей и OAuth оболочка не заводит. Именованные токены хаба остаются токенами установки, не учётными записями.

## Тесты

В репозитории HARNESS тестов оболочки нет и этим пунктом не добавляется. Хаб проверяется тестами пунктов 4 и 6.

Когда человек выберет стек и заведёт репозиторий оболочки, тот репозиторий проверяет наблюдаемое поведение:

- запрос постановки уходит на `POST /v1/runs` и не уходит на URL сервиса;
- bearer отсутствует в URL, в журнале теста и в теле `message`;
- микрофон до действия человека выключен, и тест не требует живого микрофона;
- в постановку голоса уходит строка расшифровки, не байты звука;
- `message` длиннее 8000 не отправляется;
- файл уходит на `POST /v1/blobs`, а в `message` нет байтов;
- `409` не создаёт вторую строку запуска;
- текст ответа с разметкой не исполняется как HTML;
- клиент TLS не отключает проверку сертификата;
- слушателя на `0.0.0.0` нет.

Злой вход для хаба, который оболочка не должна обходить: постановка без bearer получает `401`, `GET /health` без bearer получает `200`. Это тесты хаба, они уже требуются пунктом 4.

## Критерии готовности

В этом репозитории не появился код оболочки и не появилась зависимость UI. Фреймворк и движок распознавания не названы как выбранные. Протокол оболочки совпадает с пунктом 4 и не добавляет маршрут. Голос не становится байтами в модели. Bearer не попадает в URL. Сервис с оболочки напрямую не вызывается.
