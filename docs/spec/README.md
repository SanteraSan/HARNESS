# Спецификация HARNESS

Этот каталог — задание следующему агенту. Один пункт реализуется так, как написан его файл: методы, поля, коды и порядок относительно захвата уже выбраны. Додумывать протокол не нужно.

Канон уже собранного продукта — [PLAN.md](../PLAN.md). План расширения — [EXPANSION.md](../EXPANSION.md). Эти два файла спецификация не заменяет и не переписывает. Номера **I1–I20** ниже взяты из раздела 4 `PLAN.md`.

Пока код не изменён, работают `PLAN.md` и `.cursor/rules/`. Спецификация описывает будущее изменение. Она не разрешает править ядро мимо путей выданного пакета.

## Порядок

1. `02-contract.md`. Конверт `harness.tool.v1` и локальный манифест. Без них вызов сервиса не описан.
2. `03-slots-and-workers.md`. Слот модели берётся до вызова модели и отпускается до HTTP сервиса.
3. `04-client-protocol.md` и `05-files.md` вместе. Маршруты файлов и байты в `BLOB_ROOT`.
4. `01-services.md`. Вынос `read_file`, `list_dir`, `record_note`. Ему нужны конверт и порядок слота.
5. `06-phone.md` и `08-shells-and-voice.md`. Это требования. Пакета кода они не открывают и продукт не выбирают.
6. `07-git.md`. Целевое состояние уже есть в `dev`. Новый код ворота не ослабляет.

Пакеты этим каталогом не назначаются. Исполнитель делает один выданный пакет и не открывает следующий. Новая колонка — новый файл миграции. Файлы `migrations/001_init.sql` … `migrations/008_completion_limit.sql` не переписываются.

## Что уже есть в репозитории

Сверено с `dev` на слиянии PR #5 (`3fa9259`).

Процессы: `api`, `worker`, `telegram`. Команды: `npm run api`, `npm run worker`, `npm run telegram`. Модель вызывает только воркер. Telegram модель не вызывает.

HTTP хаба сейчас, `src/api/app.ts`:

- `GET /health` без токена, тело `{ "ok": true }`.
- `POST /v1/runs`.
- `GET /v1/runs/:id`.

Других маршрутов нет. Слушает константа `API_LISTEN_HOST` = `127.0.0.1`, порт `8787`. Тело любого запроса режется на 32 КиБ в `prepareRequest` до Hono. `requestTimeout` 30 с, `headersTimeout` 10 с, `keepAliveTimeout` 5 с. Заголовок ответа `X-Content-Type-Options: nosniff`. Ошибка клиента — `{ "reason": "<код>" }` без стека.

Постановка принимает `agent_slug`, `idempotency_key`, `message` до 8000 символов и необязательный `chat_id` строкой. Неизвестные поля постановки zod отбрасывает. Ответы: `201` и `reason: "created"`, `200` и `reason: "replay"`, `409` и `reason: "dialog_busy"` вместе с `id` и `status`. Неизвестный slug — `404` и `reason: "unknown_agent"`. Нет bearer — `401`. Пустой `HARNESS_API_TOKEN` не подходит ни к какому заголовку.

`read_file`, `list_dir` и `record_note` исполняет процесс воркера. У чтения `effect: "read"`. У `record_note` `effect: "write"`, файл только в `FILE_ROOT/out`. Повтор заметки хранится в `FILE_ROOT/out/.record-note` и тело вызова не сравнивает. Лимит чтения `FILE_ROOT` — 64 КиБ UTF-8.

Очередь захватывает запуск одним `UPDATE … FOR UPDATE SKIP LOCKED`. Оператор коммитится до модели. Пул `max: 4`. `statement_timeout` 15 с. `idle_in_transaction_session_timeout` 10 с. `chat_id` в драйвере остаётся строкой.

Воркер держит один текущий запуск и дочерние процессы не порождает. `WORKER_ID` берётся из окружения, иначе из `hostname()`. `LEASE_SECONDS` 120, `HEARTBEAT_SECONDS` 15.

Миграции на диске: `001` … `008`. Колонка `max_completion_tokens` в `008_completion_limit.sql` — предел ответа модели. Таблицы `model_slots` в коде нет. Сортировка имён миграций уже в `src/db/migrate.ts`: `localeCompare` с локалью `en` и `numeric: true`; при нуле полное имя сравнивается по кодам UTF-16.

Runtime-зависимости: `hono`, `grammy`, `postgres`, `zod`, `pino`. В devDependencies уже есть `husky` 9.1.7 и `@vitest/coverage-v8` той же версии, что `vitest` (`5.1.0`). Скрипт `prepare` — `husky`. `npm run test:coverage` пишет `coverage/lcov.info`.

CI, Husky и ruleset описаны в `07-git.md`. Они уже включены. Шага Bandit в workflow нет.

Пакет M3-P7 в `PLAN.md` имеет статус `ready`. Пустого списка инструментов для чата `coder-cloud` и поля `reasoning_effort` в коде ещё нет.

## Какие правила ядра меняются

Меняется место исполнения трёх имён и фраза границы «Пула нет».

- Несколько процессов `worker` разрешены. По умолчанию процесс один. **I13** не меняется: внутри процесса второй `claim` не начинается.
- **I12** в части «сетевых вызовов в инструментах нет» и в части вызова `read_file`, `list_dir`, `record_note` из процесса воркера. После выноса эти три имени вызывает раннер по HTTP файлового сервиса. Запрет имён **I3** манифест не отменяет. Фраза **I12** про `effect: "read"` описывает срез M1. `record_note` остаётся `effect: "write"`.
- **I19** для `FILE_ROOT` переезжает в файловый сервис. Хаб тот же `realpath` применяет к своему `BLOB_ROOT`. После выноса воркер `FILE_ROOT` не открывает.

Не меняются **I1**, **I2**, **I3**, **I4**, **I5**, **I6**, **I7**, **I8**, **I9**, **I10**, **I11**, **I13**, **I14**, **I15**, **I16**, **I17**, **I18**, **I20**. **I19** соблюдается на том корне, который процесс открывает.

**I1** остаётся буквально. Очередь не импортирует клиент модели и не импортирует клиент сервиса. После коммита захвата сервис вызывает раннер.

**I15** для `package.json` хаба: не добавлять Ajv, gRPC, ORM, Redis, LangGraph, Claude Agent SDK и `helmet`. `husky` и провайдер покрытия `vitest` уже стоят как devDependencies.

Слово «слот» в `008_completion_limit.sql` и таблица `model_slots` — разные вещи. Файл `008` не переписывается.

## Правила, которые остаются во всех пунктах

- Значения SQL только через помеченный шаблон `postgres`. Имена таблиц и столбцов — литералы. `sql.unsafe` с вводом пользователя запрещён.
- `chat_id` в JavaScript — строка. `Number(chatId)` не вызывать. Сервису `chat_id` не отправляется.
- `locked_until` считается через `now()` Postgres.
- Захват — один `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1)`. Отдельные `SELECT`, затем `UPDATE` по id, для захвата не писать.
- `redact` выполняется до вставки шага и до следующего сообщения модели. В pino не попадают тело ответа шлюза, `Authorization`, токен бота, `DATABASE_URL`, стек, сырые аргументы инструмента, способность и секрет сервиса.
- JSON инструмента в `content` при пустых `tool_calls` даёт шаг `parse_error`, статус `failed`, пустой `final_text`. Ремонтная реплика модели не отправляется.
- Ошибка инструмента ожидаема: запуск жив, шаг записан. Потеря лока: `succeeded` не ставится, новые шаги не пишутся. Необработанное исключение завершает процесс.
- Путь: `realpath` корня и цели, префикс с разделителем. `..`, абсолютный путь снаружи, симлинк наружу и каталог с общим префиксом имени — ошибка.
- Нет `child_process` со строкой оболочки, нет `eval`, нет `new Function`. `execFile` без оболочки допустим только там, где он уже есть у хука git.
- Идентификаторы — `crypto.randomUUID` или `crypto.randomBytes`. Не `Math.random` и не `Date.now`.
- Ключи `__proto__`, `constructor`, `prototype` не копируются. На контракте сервиса неизвестное поле — отказ. Тихое отбрасывание оставлено только `POST /v1/runs`.
- Перед регулярным выражением строка обрезается. Квантификатор на пользовательском тексте не шире `{1,200}`. Ключевое слово `pattern` из JSON Schema в `RegExp` не компилируется.
- Слушать `0.0.0.0` нельзя. `rejectUnauthorized: false` и `NODE_TLS_REJECT_UNAUTHORIZED=0` нельзя.
- Секрет сравнивается через `crypto.timingSafeEqual`. При разной длине буферов функция бросает ошибку, поэтому длины равны до вызова. Для токена неизвестной длины сравниваются SHA-256, оба по 32 байта.
- Тестовая база кончается на `_test`. Хелпер при другом имени падает до первого `delete`. `DROP DATABASE` и команды против рабочей базы из теста запрещены.
- В фикстурах секрет — строка вида `test-secret-value`, не боевой ключ.

## Нужно решение человека

Имя и URL репозитория контракта и имя и URL репозитория файлового сервиса этот каталог не назначает: `EXPANSION.md` оставляет оба имени человеку. Имена базы `harness_files`, роли `harness_files_app` и тестовой базы `harness_files_test` — имена Postgres, не имена git-репозиториев. Остальные развилки пунктов закрыты файлами этого каталога. Продукт туннеля, фреймворк оболочки, стек UI телефона и движок распознавания не выбираются: для них записаны требования.
