# HARNESS — расширение

Подробности пунктов 1–7 — в этом файле. Отложены только стек оболочек, движок распознавания речи и продукт туннеля. Пакеты здесь не открываются и кода не назначают.

Канон уже сделанного и открытых пакетов — [PLAN.md](PLAN.md). Этот файл его не заменяет. M3-P7, админка M3-P4 и картинки M4 остаются там. Telegram-бот пока остаётся внутри HARNESS: выносить его или оставить в поставке библиотеки решаем позже.

Ядро не меняет роль. Это хаб: очередь, воркеры, журнал, учёт токенов и вызов модели. Модель выбирает сервис и пишет короткий ответ. Работу делает подключённый сервис.

## Принятые решения

Их не переоткрывают при нарезке пакетов.

1. Подробно выносятся `read_file`, `list_dir` и `record_note`. Jira и длинный текст — короткие примеры того же контракта. Проекта интеграции нет.
2. Каждый сервис — отдельный репозиторий. Хаб знает контракт и локальный манифест. Кода сервиса в этом репозитории нет.
3. Путь телефона — требования к туннелю. Продукт туннеля этот документ не выбирает.
4. Протокол клиента, файлы и границы телефона описаны здесь. Стек веб-оболочки, десктопа, телефонного приложения и движок распознавания речи не выбираются.
5. Telegram-бот остаётся процессом поставки. Ниже — критерии, по которым его позже можно сделать клиентом того же HTTP. Вынос как миграция не проектируется.
6. Пул — несколько процессов `worker`. В процессе один текущий запуск. Число задаёт установка, по умолчанию 1. Установщик записывает `model_slots`. Для Qwen это уже выбранное человеком значение `num_parallel`. Хаб имя модели в это число не переводит.
7. Один чат сериализуется. Параллельность — между разными чатами и только в пределах слотов и свободных процессов.
8. Транзакция захвата коммитится до вызова модели и до вызова сервиса. Соединение базы не держится `idle in transaction` на время модели или сервиса.
9. Файл клиента лежит в `BLOB_ROOT` на машине хаба. Сервис получает одноразовую способность, не байты в контекст модели.
10. Клиент говорит с хабом развитием текущего HTTP. Контракт хаб↔сервис отдельный и версионный.
11. Хаб слушает только `127.0.0.1`. Наружу смотрит только туннель, и он заканчивается на локальном порту.
12. Токены считает хаб по полю `usage` ответа шлюза. Сервис сообщает результат и `duration_ms`. Чужие токены в ответе — отказ разбора.
13. Секрет сервиса не попадает в модель, в журнал и в репозиторий сервиса.
14. Работа в долгие ветки входит только через pull request. Порог, который ломает сборку, и адрес привязки SonarQube зафиксированы в пункте 7. Workflow адрес не содержит: CI читает переменную `SONAR_HOST_URL`.

## Какие правила ядра этот документ заменяет

Инварианты ниже — номера из раздела 4 `PLAN.md`. Пока код расширения не написан, действуют они, а не этот файл.

Заменяется место исполнения и фраза «пула нет»:

- Пункт 11 раздела 3 плана и фраза границы «Пула нет». Несколько процессов `worker` разрешены. Число по умолчанию — 1. **I13** не заменяется: один процесс — один текущий запуск. Внутри процесса второй `claim` не появляется.
- **I12** в части «сетевых вызовов в инструментах нет» и в части вызова `read_file`, `list_dir`, `record_note` из процесса воркера. После выноса эти три имени исполняет файловый сервис. Запрет имён **I3** остаётся в коде хаба и манифестом не отменяется. Первая фраза I12 про `effect: "read"` описывает срез M1. В дереве `record_note` уже имеет `effect: "write"`. Этот документ не возвращает его к чтению.
- Разделы 6 и 11 плана, где эти три инструмента выполняются внутри воркера. Правила пути **I19** переезжают в файловый сервис вместе с `FILE_ROOT`. Хаб для каталога клиента заводит отдельный корень `BLOB_ROOT` и проверяет его тем же `realpath`.

Не заменяются: **I1**, **I2**, **I3**, **I4**, **I5**, **I6**, **I7**, **I8**, **I9**, **I10**, **I11**, **I13**, **I14**, **I15**, **I16**, **I17**, **I18**, **I19**, **I20**.

**I15** для хаба сохраняется: в `package.json` хаба не добавляются Ajv, gRPC, ORM, Redis, LangGraph, Claude Agent SDK и `helmet`. Исключение пункта 7 — dev-зависимость `husky` и провайдер покрытия тестов той же версии `vitest`, которая уже стоит. Это не runtime. Сервисный репозиторий в список M1 не входит и ниже ограничен отдельно.

**I1** сохраняется буквально. Очередь не импортирует клиент модели и не импортирует клиент сервиса. После коммита захвата раннер сам вызывает сервис.

Слово «слот» в `migrations/008_completion_limit.sql` — про окно контекста и колонку `max_completion_tokens`. Таблица `model_slots` этого документа — про одновременные ответы модели. Это разные вещи. `008` не переписывается.

## Правила, которые расширение не ослабляет

Они обязательны и для хаба, и для файлового сервиса.

- Значения SQL только через помеченный шаблон `postgres`. `sql.unsafe` с вводом пользователя запрещён. Имена таблиц и столбцов — литералы.
- `chat_id` в JavaScript — строка. `Number(chatId)` не вызывать. Сервису `chat_id` не отправляется.
- `locked_until` считается через `now()` Postgres. Часы процесса для аренды не используются.
- Захват запуска и захват слота — один `UPDATE … FOR UPDATE SKIP LOCKED`. Отдельные `SELECT`, затем `UPDATE` по id, для захвата не писать.
- `redact` выполняется до вставки шага и до следующего сообщения модели. В pino не попадают тело ответа шлюза, `Authorization`, токен бота, `DATABASE_URL`, стек, сырые аргументы инструмента, способность и секрет сервиса.
- JSON инструмента в `content` при пустых `tool_calls` даёт шаг `parse_error`, статус `failed`, пустой `final_text`. Сервис при этом не вызывается. Ремонтная реплика модели не отправляется.
- Ошибка инструмента ожидаема: запуск жив, шаг `tool_result` записан. Потеря лока запуска: `succeeded` не ставится, новые шаги не пишутся. Необработанное исключение завершает процесс.
- Путь: `realpath` корня и цели, префикс с разделителем. Запрещены `..`, абсолютный путь снаружи, симлинк наружу, каталог с общим префиксом имени.
- Нет `child_process` со строкой оболочки, нет `eval`, нет `new Function`.
- Идентификаторы — `crypto.randomUUID` или `crypto.randomBytes`. Не `Math.random` и не `Date.now`.
- Ключи `__proto__`, `constructor`, `prototype` не копируются. На контракте сервиса неизвестное поле — отказ версии. Тихое отбрасывание оставлено только текущей постановке `POST /v1/runs`, где схема и сейчас читает свои поля.
- Лимиты тела и таймауты HTTP явные. Ответ несёт `X-Content-Type-Options: nosniff`. Пакет `helmet` не добавляется.
- Регулярное выражение по вводу — после обрезки и с квантификатором не шире `{1,200}`. Голый `*` и `+` на пользовательском тексте не ставятся. Ключевое слово `pattern` из JSON Schema хаб в `RegExp` не компилирует.
- Новая колонка хаба — новый файл миграции. `001_init.sql` и уже применённые файлы не переписываются. Файлы миграции этим документом не создаются.
- Тестовая база кончается на `_test`. Хелпер при другом имени падает до первого `delete`. `DROP DATABASE` и команды против рабочей базы из теста запрещены.
- Слушать `0.0.0.0` нельзя. `rejectUnauthorized: false` и `NODE_TLS_REJECT_UNAUTHORIZED=0` нельзя.
- Секрет сравнивается через `crypto.timingSafeEqual` по буферам одинаковой длины. Документация Node 22: при разной длине функция бросает ошибку, поэтому перед вызовом длины равны. Для токена неизвестной длины сравниваются SHA-256, оба по 32 байта.

Опора по угрозам: [OWASP Node.js Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Nodejs_Security_Cheat_Sheet.html) (лимит тела по типу содержимого, запрет `eval` и `child_process.exec`, ReDoS) и [OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) — BOLA, аутентификация, лишние поля, расход ресурсов, подмена функции, SSRF, конфигурация, инвентарь API, недоверенный ответ чужого API.

## 1. Сервисы вместо зашитых инструментов

`read_file`, `list_dir` и `record_note` уходят из процесса воркера в отдельный сервис. Воркер их больше не вызывает сам. Он передаёт имя, аргументы и идентификатор запуска и получает короткий текст.

Будущие сервисы, включая Jira и генерацию длинного текста, подключаются так же. Свой экран сервиса хаб не рисует. Хаб отдаёт итог или ссылку, дальше человек работает в интерфейсе сервиса, если он есть.

### Назначение

Файловый сервис — один отдельный репозиторий и один процесс. Он единственный, кто открывает `FILE_ROOT`. Хаб после выноса этот каталог не читает и не пишет.

В текущем дереве все три имени ещё внутри воркера. `read_file` и `list_dir` имеют `effect: "read"`. `record_note` имеет `effect: "write"`, пишет только в `FILE_ROOT/out` и помнит повтор в файлах `FILE_ROOT/out/.record-note`. Повтор ключа сейчас возвращает первый текст и тело вызова не сравнивает. После выноса источник правды повтора — таблица сервиса, не этот каталог. Старые файлы журнала не импортируются.

`create_subtask`, `approve`, кроны, секреты коннекторов и раннер Claude SDK этим пунктом не переносятся. Пустой список инструментов чата `coder-cloud` из M3-P7 сохраняется: у такого хода сервиса нет, даже если имя есть в манифесте.

### Чего в пункте нет

Нет экрана сервиса, нет Jira-клиента, нет второй модели внутри хаба, нет подхвата инструментов по сети, нет пула потоков внутри одного процесса Node.

### Угрозы

Модель просит имя из запретного списка или имя, которого нет в манифесте. Сервис подменяет ответ и дописывает поля токенов. Аргумент содержит путь наружу, секрет или огромную строку. Повтор записи после таймаута создаёт второй файл. Упавший воркер оставляет запуск `succeeded`. Описание инструмента в манифесте пытается переписать системный промпт. Запрос уходит на чужой URL, который подсказал ответ модели.

### Технологии

Вызов — HTTP JSON на `127.0.0.1`. У хаба уже есть HTTP, zod и предел тела 32 КиБ. gRPC не берётся: это второй стек, HTTP/2 и разбор protobuf, шире поверхность и новый список зависимостей. stdio не берётся: хаб тогда порождал бы процесс сервиса, а строка оболочки для инструментов запрещена.

Клиент — `fetch` из Node 22. `redirect: "error"`, чтобы ответ сервиса не уводил хаб на другой хост (API7 и API10). Таймаут — `AbortSignal`. Тело читается с потолком `SERVICE_RESPONSE_BYTES`.

Проверка входа и выхода на хабе — ручной строгий zod, без новой зависимости. Ajv в хаб не ставится. У Ajv 6.12.2 была prototype pollution, [CVE-2020-15366](https://nvd.nist.gov/vuln/detail/CVE-2020-15366). При включённом `$data` была ReDoS, [CVE-2025-69873](https://github.com/advisories/GHSA-2g4f-4pwh-qvx6), закрытая в 6.14.0 и 8.18.0. Даже закрытые версии не причина тащить компилятор схем на путь модели: хаб тогда исполнял бы чужой `pattern`. Канон схемы лежит в репозитории контракта. Хаб держит ручную копию конверта `harness.tool.v1`.

Файловый сервис на лупбэке слушает только `127.0.0.1` и порт из манифеста. Хаб порт не угадывает: он читает `base_url` манифеста. Номер порта этой машины в документ не пишется.

Если сервис не на лупбэке, в манифесте литерал частного IP, не DNS-имя: иначе подмена DNS уводит вызов. Канал — TLS. `rejectUnauthorized` остаётся значением по умолчанию `true` ([tls Node 22](https://nodejs.org/docs/latest-v22.x/api/tls.html)). Рядом `checkServerIdentity` сверяет `fingerprint256` сертификата с отпечатком из манифеста через `timingSafeEqual`. Слушать `0.0.0.0` сервису нельзя.

База файлового сервиса — тот же Postgres `127.0.0.1:5442`, отдельная база `harness_files`, роль `harness_files_app`. Пароль в этот документ не пишется. Роль не имеет `CONNECT` к базе `harness` и не читает `runs`. Тестовая база — `harness_files_test`. ORM, Redis, LangGraph и Claude Agent SDK сервису не предлагаются. Зависимости сервиса: Node 22, `postgres`, `zod`, `pino`. HTTP поднимается через `node:http`, без второго фреймворка.

### Протокол

Версия конверта — `harness.tool.v1`. Хаб вызывает:

`POST /v1/tools/{name}`

Заголовки:

- `Authorization: Bearer <секрет сервиса>`
- `Content-Type: application/json; charset=utf-8`
- `X-Contract-Version: harness.tool.v1`
- для `effect: "write"` обязателен `Idempotency-Key`

Тело:

```json
{
  "contract": "harness.tool.v1",
  "run_id": "00000000-0000-4000-8000-000000000010",
  "tool_call_id": "call_1",
  "agent_id": "00000000-0000-4000-8000-000000000001",
  "name": "read_file",
  "arguments": { "path": "notes/a.txt" }
}
```

`name` в пути и в теле совпадают. Иначе `400` и `reason: "invalid_body"`. Неизвестное поле — `400` и `reason: "unknown_field"`. Другое значение `contract` — `400` и `reason: "unsupported_version"`. Это отказ версии, не тихий пропуск.

Успех, `200`:

```json
{
  "contract": "harness.tool.v1",
  "ok": true,
  "text": "notes/a.txt",
  "truncated": false,
  "duration_ms": 4,
  "blobs": []
}
```

Ожидаемая ошибка инструмента тоже `200`, с `"ok": false` и коротким `error`, без стека. Запуск при этом жив.

Поля `prompt_tokens`, `completion_tokens`, `cost_usd` и любое иное поле контракт `v1` не содержит. Хаб такой ответ не отдаёт модели и пишет шаг с `error: "unknown_field"`.

Коды сервиса, которые видит хаб:

| Код | `reason` | Смысл |
| --- | --- | --- |
| 400 | `invalid_body`, `unknown_field`, `unsupported_version` | тело или версия |
| 401 | `unauthorized` | bearer |
| 404 | `unknown_tool` | имени нет у этого сервиса |
| 409 | `idempotency_conflict` | тот же ключ, другой хеш |
| 409 | `idempotency_in_progress` | тот же ключ ещё выполняется |
| 413 | `payload_too_large` | тело больше 32 КиБ |

`GET /health` сервиса без секрета возвращает `{ "ok": true }`. В теле нет версии пакетов и нет путей.

Аргументы трёх инструментов остаются теми, что уже в коде, с одной заменой у записи. `read_file`: `path`, строка 1..4096. `list_dir`: необязательный `path`, иначе каталог корня, один уровень. `record_note`: `path` и `text`. Поле `idempotency_key` внутри аргументов модели больше не источник правды. Ключ записи ставит хаб. Если модель прислала своё поле, сервис отвечает `unknown_field` либо хаб снимает его до отправки. В плане выбран второй путь для совместимости хода: хаб удаляет это поле из копии аргументов, в хеш входит уже копия без него, сервису уходит копия без него.

Текст `record_note` вместе с JSON обязан уложиться в 32 КиБ. Схема в коде сейчас пишет потолок 64 КиБ, но разбор аргументов обрывается на 32 КиБ. Наружу уходит более жёсткий потолок.

### Данные и порядок

Манифест перечисляет сервис `files`, `base_url`, имена, `effect`, описание, схему аргументов для модели и отпечаток TLS, если адрес не лупбэк. Секрета в манифесте нет.

Порядок одного хода, после того как постановка уже закоммичена:

1. Воркер делает `reapExpired` и один `claimNext`. Оператор захвата коммитится сам. Модель ещё не вызвана.
2. Стартует heartbeat запуска каждые 15 с. `false` — выход без `finish`.
3. Перед `ChatModel.complete` захватывается слот отдельным коротким оператором. Слот отпускается сразу после ответа шлюза и до сервиса.
4. `interpretModelOutput`. Ветка `parse_error` сервис не вызывает.
5. Для каждого `tool_calls[].id`: запрет, затем allowlist агента, затем имя из манифеста. Иначе шаг `policy_deny` и HTTP нет.
6. Аргументы длиннее 32 КиБ не парсятся. В сервис уходит усечённая копия без секретных полей способности.
7. Соединение базы к этому моменту не держит транзакцию. `fetch` идёт со своим таймаутом: 30 с на чтение, 60 с на запись.
8. Ответ проходит строгую схему. `text` режется до 8000 символов, затем `redact`, затем попадает в сообщение роли `tool` и в выдержку журнала не длиннее 2000.
9. `duration_ms` пишется в `run_steps` только пока лок запуска ещё наш.
10. `finish` возможен только при своём `locked_by` и `status = 'running'`.

Журнал сейчас кладёт в `request_excerpt` сырые аргументы после `redact`. Для вызова сервиса выдержка — имя инструмента и hex SHA-256 канонического тела. Сырой JSON аргументов в pino и в выдержку не пишется.

Потеря аренды запуска посередине HTTP: сокет обрывается, `finish` не вызывается. Запись на сервисе может успеть завершиться. Повтор того же `tool_call_id` безопасен. Повтор всего запуска после reaper — новый ход модели и новый `tool_call_id`, значит новый ключ. Это принятый предел ключа `<run_id>:<tool_call_id>`. Подменять его хешем аргументов нельзя.

`provider = external` по-прежнему выбирает `ClaudeSdkRunner`. Этот документ не включает SDK. Пока клиент SDK не установлен, ветка и сейчас падает с `sdk_not_installed`. Три файловых имени через неё не исполняются внутри воркера.

### Отказы

Таймаут и обрыв соединения — ошибка инструмента, запуск жив. Для записи хаб повторяет один раз тот же ключ и тот же хеш. Для чтения повтора нет.

`409` с другим хешем повторно не отправляется. `409` «ещё выполняется» — один повтор после паузы в 1 с, затем ошибка инструмента.

Чужая версия и лишнее поле до модели не доходят. Слишком большое тело хаб не отправляет: аргументы режутся ещё локальным пределом 32 КиБ. Ответ больше `SERVICE_RESPONSE_BYTES` обрывается, в модель уходит короткая ошибка `payload_too_large`.

Сервис недоступен. Хаб не исполняет инструмент локально взамен. Шаг — ошибка, цикл модели продолжается, пока лок жив и не кончился `max_steps`.

Потеря слота во время модели: `succeeded` не ставится. Если лок запуска ещё наш, `finish(failed)` с `error = slot_lost`. Если лок запуска тоже потерян, записей больше нет.

### Безопасность разработки

Репозиторий сервиса не содержит токена, `DATABASE_URL` хаба и примеров ключей, похожих на настоящие. В нём `.env.example` с пустыми значениями. Ревью сверяет дифф с I2, I3, I4, I7, I19 и с этим протоколом. Зависимость вне списка `postgres`, `zod`, `pino` — стоп. Тесты сервиса ходят в `harness_files_test`.

Контрактный репозиторий хранит JSON Schema и примеры. Хаб его по сети на старте не скачивает. Имя репозитория выбирает человек при создании. URL этот документ не назначает.

### Безопасность эксплуатации

Процесс сервиса — пользователь без входа в систему, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ReadWritePaths` только на `FILE_ROOT`. Каталоги хаба, `BLOB_ROOT` и домашний каталог ему не видны. Юнит не слушает не-лупбэк.

Секрет сервиса лежит в файле режима `0400` вне обоих репозиториев. На стороне сервиса в базе и на диске хранится только SHA-256. Ротация: новый секрет записывается в файл хаба и новым хешем на сервисе, оба процесса перезапускаются, старый хеш удаляется. Журнал значение не видит.

Резервная копия сервиса — база `harness_files` вместе с `FILE_ROOT`. Восстановление одной половины без другой даёт запись без файла или файл без журнала идемпотентности. Это чинится человеком, автоматического сличения документ не добавляет.

Лог сервиса: `run_id`, имя инструмента, `duration_ms`, код ошибки. Не аргументы, не `Authorization`, не текст файла.

### Тесты

Команда сервиса — его собственный `npm test` против `harness_files_test`. На хабе — `npm test` с фейковым HTTP сервиса, без живого `qwen`.

Злые входы:

- `../`, абсолютный путь, симлинк наружу, каталог `FILE_ROOT-evil`;
- имя `Bash` в манифесте и в allowlist не вызывает HTTP;
- неизвестное имя не вызывает HTTP;
- JSON инструмента в `content` не вызывает HTTP;
- лишнее поле ответа и поле `prompt_tokens` не попадают в историю модели;
- тело аргументов больше 32 КиБ не уходит в сокет;
- тот же ключ и тот же хеш не создают второй файл;
- тот же ключ и другой хеш дают 409 и не создают файл;
- обрыв сокета после записи: повтор возвращает первый результат;
- фейковый токен в `text` отсутствует в `run_steps` и во втором запросе модели;
- heartbeat `false` во время вызова: `finish` не вызван;
- `coder-cloud` не получает список этих инструментов.

### Критерии готовности

Воркер не импортирует `src/tools/read-file.ts`, `list-dir.ts`, `record-note.ts`. Юнит воркера не имеет `FILE_ROOT` в `ReadWritePaths`. Три имени по-прежнему видны модели локального агента, если они есть в allowlist и в манифесте. Запрет имён сильнее обоих списков. Очередь не импортирует клиент сервиса.

### Пример. Jira

Отдельный репозиторий. Контракт тот же, `harness.tool.v1`.
Хаб берёт имя из локального манифеста и не знает проекта Jira.
Эффект `write`. Токен Jira только в окружении этого сервиса.
В модель, в журнал и в репозиторий сервиса он не входит.
Модель передаёт короткие поля: проект, заголовок, текст.
Сервис создаёт задачу своим клиентом Jira.
Обратно уходит строка вида «создана задача PROJ-1».
Тело задачи и сырой ответ Jira в контекст модели не копируются.
Ключ — `Idempotency-Key` со значением `<run_id>:<tool_call_id>`.
Сервис хранит ключ, хеш тела и первый ответ.
Тот же ключ и тот же хеш возвращают первую строку, второй задачи нет.
Тот же ключ и другой хеш дают `409`, новой задачи нет.
Таймаут для хаба — ошибка инструмента, запуск жив.
Один повтор транспорта идёт с тем же ключом и тем же хешем.
Чужая версия конверта задачу не создаёт.
Хаб пишет `duration_ms`. Полей токенов в ответе нет.
Если сервис их прислал, разбор отвергается и суммы запуска не меняются.
Экран Jira хаб не рисует.
Человек открывает задачу по ключу из итога.

### Пример. Длинный текст

Отдельный репозиторий. Контракт тот же, `harness.tool.v1`.
Эффект в манифесте — `read` или `write`, по смыслу вызова.
Сервис может вызвать свою модель и потратить свои токены.
Хабу он эти токены не объявляет.
`prompt_tokens`, `completion_tokens` и `cost_usd` в ответе — отказ разбора.
В суммы запуска эти числа не прибавляются.
В модель хаба входит короткий итог не длиннее 8000 символов.
Если текст длиннее, сервис сдаёт его хабу байтами blob и возвращает id.
Модель видит идентификатор, не тело.
Секрет своей модели остаётся в окружении сервиса.
В репозиторий сервиса и в журнал хаба этот секрет не входит.
Для `write` сервис хранит ключ `<run_id>:<tool_call_id>` и хеш тела.
Тот же ключ и тот же хеш возвращают первый итог.
Вторая генерация при этом не начинается.
Тот же ключ и другой хеш дают `409`.
Хаб пишет только `duration_ms` и короткий текст после `redact`.
Свой экран генерации хаб не рисует.
Дальше человек открывает файл по тому же id.

## 2. Закрытый контракт

У контракта есть версия. Сервис не добавляет своё поле к текущей версии. Неизвестное поле хаб отвергает. Новая возможность — отдельная версия контракта, не тихая добавка.

Контракт описывает инструмент: имя, описание для модели, схему аргументов, эффект чтения или записи и вызов. Число воркеров и число одновременных ответов модели в контракт не входят. Это настройка установки хаба. Сервис её не меняет.

На вызове действуют четыре правила, подробности позже:

- секрет не попадает в модель, в журнал и в репозиторий сервиса;
- у аргументов, файла и текста ответа сервиса есть предел размера, чтобы один вызов не забил окно модели;
- повтор того же ключа не делает побочный эффект второй раз;
- токены считает хаб по ответу шлюза. Сервис сообщает свой результат и длительность, чужие токены не объявляет.

Подробности четырёх правил — ниже. Новая возможность — контракт `harness.tool.v2` отдельным документом. Хаб `v1` её не принимает.

### Назначение

Два документа. Репозиторий контракта хранит канон: JSON Schema 2020-12, примеры и текст версии. Хаб хранит локальный манифест, который кладёт оператор, и ручной zod конверта.

Манифест описывает уже известные инструменты. Он не содержит `model_slots`, числа воркеров и секретов.

### Чего в пункте нет

Нет реестра инструментов в сети, нет автообновления на старте, нет права сервиса прислать новую схему в ответе.

### Угрозы

Лишнее поле протаскивает секрет или токены. Схема с `pattern` вешает процесс. Манифест подменён на диске. Два разных тела записи сходятся в один ключ. Сервис объявляет чужой расход токенов, и хаб портит учёт.

### Технологии

JSON Schema запрещает лишние поля. У плоского объекта это `additionalProperties: false`. У объекта, собранного через `allOf`, этого мало: ключевое слово видит только соседние `properties`. Для составной схемы дополнительно `unevaluatedProperties: false`. Так написано в [справочнике JSON Schema](https://json-schema.org/understanding-json-schema/reference/object).

Хаб эту схему не исполняет. Он проверяет конверт зодом, который перечисляет поля и отвергает остальные. Расхождение ручной копии и канона ловится тестом на версию `harness.tool.v1` и на список имён полей, а не Ajv внутри процесса.

Манифест — файл из `SERVICES_MANIFEST`. Рядом переменная `SERVICES_MANIFEST_SHA256`, 64 hex-символа. На старте хаб считает SHA-256 файла и сравнивает 32 байта через `timingSafeEqual`. Иначе процесс выходит до приёма трафика. `SIGHUP` манифест не перечитывает. Смена — новый файл, новая сумма, перезапуск.

Идемпотентность записи следует черновику [draft-ietf-httpapi-idempotency-key-header-08](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header/) от 22 октября 2026, срок до 25 апреля 2027. Это ещё не RFC. Заголовок — `Idempotency-Key`, строка structured field в кавычках. Отпечаток — SHA-256 канонического тела. Черновик на другое тело рекомендует `422`, а на ещё не законченный запрос — `409`. Решение этого плана: и другой хеш, и незавершённый запрос отвечают `409`. Код `422` не используется, чтобы у хаба был один отказ конфликта. Повторный побочный эффект запрещён в обоих случаях. Чтение заголовок может прислать, но сервис строку идемпотентности для `effect: "read"` не создаёт.

Канон тела для хеша: UTF-8, без лишних пробелов, ключи объекта по байтам UTF-8, порядок массива сохранён. Способности и секретов в этом теле нет.

Токены по-прежнему суммирует раннер из `usage.prompt_tokens` и `usage.completion_tokens` ответа LiteLLM. `duration_ms` сервиса в эти суммы не входит. В шаге запуска для локального провайдера `cost_usd` остаётся 0, как сейчас. Сервис стоимость не присылает.

### Протокол манифеста

Файл `harness.services.v1`:

```json
{
  "contract": "harness.services.v1",
  "services": [
    {
      "id": "files",
      "base_url": "http://127.0.0.1:<port>",
      "tools": [
        {
          "name": "read_file",
          "effect": "read",
          "description": "Читает текстовый файл UTF-8 внутри рабочего каталога.",
          "accepts_blobs": false
        }
      ]
    }
  ]
}
```

Полная схема аргументов для модели лежит тут же, полями `type`, `properties`, `required`, `additionalProperties`, `maxLength`, `minLength`, `enum`, `maxItems`. Поле `pattern`, `$ref` на сеть и `$data` делают манифест недействительным, процесс не стартует.

`description` не длиннее 500 символов. Имя из списка запрета выбрасывается при сборке списка для модели, даже если манифест и allowlist его содержат. Неизвестное модели имя, которого нет после этого пересечения, не вызывается.

Отпечаток сертификата для не-лупбэка — поле `tls_fingerprint256` в манифесте. Это не секрет, это пин публичного сертификата. Секрет bearer в файл не кладётся.

### Данные

Ключ записи хранит сервис:

- `idempotency_key` — текст `<run_id>:<tool_call_id>`;
- `body_sha256` — 32 байта;
- `state` — `started` или `done`;
- ответ, который можно вернуть повторно;
- `created_at` от `now()`.

Вставка `started` коммитится до побочного эффекта. Совпадение ключа и хеша при `done` возвращает сохранённый ответ. Другой хеш — `409` без записи. Тот же ключ в `started` — `409` без второй записи. Падение между коммитом и файлом оставляет `started`: повтор не пишет файл второй раз и сообщает ошибку инструмента. Окно честное и узкое. Через 72 часа строка может быть удалена коротким запросом в начале следующего вызова, не больше 20 строк за раз. Отдельный крон не заводится.

Чтение эту таблицу не трогает.

### Отказы

Нет файла манифеста, чужая сумма, чужая версия конверта, инструмент без `effect`, два сервиса на одно имя — процесс хаба не слушает порт. Вызов с неизвестным именем при живом процессе — `policy_deny`, не сеть.

Протухшая строка идемпотентности старше 72 часов для хаба выглядит как первый вызов. Поэтому срок — часть контракта, и его не укорачивают молча на одном конце.

### Безопасность разработки

Репозиторий контракта без секретов и без боевых URL с паролем. Примеры используют фиктивные uuid. Ревью схемы смотрит `additionalProperties` и `unevaluatedProperties`. PR хаба, который добавляет поле в zod и не поднимает версию, не сливается.

Версии зависимостей хаба не ослабляются до `*` и `latest`. `package-lock.json` остаётся рядом с `package.json`.

### Безопасность эксплуатации

Файл манифеста пишет оператор, режим не слабее `0444`, владелец — не процесс, которому хватило бы записи. Каталог манифеста не входит в `ReadWritePaths` воркера. Секрет сервиса — отдельный файл `0400`. Ротация секрета не требует новой версии контракта. Ротация контракта требует нового имени версии и одновременной поддержки старой, пока хаб и сервис не перезапущены на одну версию. Смешанная пара получает `unsupported_version`, вызов не исполняется.

В лог не пишется тело манифеста, если вдруг в нём оказался секрет: в лог идут `service id`, имя инструмента и результат сверки суммы.

### Тесты

- лишнее поле конверта отвергается;
- ключи `__proto__`, `constructor`, `prototype` отвергаются;
- `pattern` в манифесте не даёт стартовать;
- сумма файла не сошлась — процесс конфигурации падает до сети;
- запрещённое имя не попадает в инструменты модели;
- чтение дважды не пишет строку идемпотентности;
- запись с тем же ключом и тем же хешем не делает второй эффект;
- запись с тем же ключом и другим хешем — 409;
- ответ с `prompt_tokens` не меняет суммы запуска;
- `duration_ms` виден в шаге и не прибавляется к токенам.

### Критерии готовности

Хаб отказывает на неизвестном поле `v1`. Список для модели строится из манифеста, allowlist и запрета. Числа воркеров и слотов в контракте отсутствуют. Секрета нет в репозитории сервиса, в журнале и в следующем запросе модели.

## 3. Слоты модели и пул воркеров

По умолчанию один воркер и один слот модели.

Сколько слотов и воркеров поднять, решает тот, кто ставит HARNESS и подключает модель. Для Qwen это `num_parallel`, для другой модели — её собственный предел одновременных ответов. Хаб эти числа не вычисляет. Пул воркеров в коде будет, из коробки он равен одному.

Один чат по-прежнему сериализуется. Параллельность — между разными чатами и запусками, в пределах настроенных слотов.

### Назначение

Слот — право одного хода модели. Строк в таблице ровно `MODEL_SLOTS`. Хаб строки из имени модели не создаёт и не удаляет. Процессы воркера поднимает установка, не код `worker.ts`. Сейчас `runWorker` прямо пишет, что пул не создаётся, и держит один запуск на процесс. Это остаётся верным внутри процесса.

### Чего в пункте нет

Нет чтения `num_parallel` у Ollama, нет очереди внутри процесса, нет Docker и Kubernetes как способа получить вторую копию, нет отдельного лимита для сервиса. Сервис слот модели не занимает.

### Угрозы

Два процесса с одним `WORKER_ID` продлевают чужой лок. Хаб сам поднимает число слотов по имени `qwen` и переполняет карту. Слот держится на время файлового сервиса, и модель простаивает. Потеря слота помечает запуск успешным. Захват слота написан двумя шагами и берёт одну строку дважды.

### Технологии

Аренда слота повторяет аренду запуска: короткий `UPDATE`, `now()`, heartbeat, просрочка возвращает слот. Образец захвата запуска уже в `src/queue/run-queue.ts`.

Число процессов задают template units systemd, экземпляр `harness-worker@<id>.service`. `WORKER_ID=%i`. Значение по умолчанию из `hostname()` остаётся только для одного ручного `npm run worker`. Два ручных процесса без разных `WORKER_ID` — ошибка установки: они сольют локи. Код по-прежнему не порождает дочерние воркеры.

`MODEL_SLOTS` — целое не меньше 1, по умолчанию 1. На старте `count(*)` из `model_slots` обязан совпасть. Иначе процесс выходит до захвата.

### Протокол аренды

Миграция `migrations/009_model_slots.sql`. Файл этим документом не создаётся. `001` не меняется.

```sql
create table model_slots (
  slot_index integer primary key check (slot_index >= 1),
  locked_by text,
  locked_until timestamptz,
  run_id uuid
);
```

Строки `1..N` вставляет установщик отдельным SQL, не эта миграция. Пока строка занята, число не меняют.

Снятие просрочки не трогает `runs`:

```sql
update model_slots
set locked_by = null,
    locked_until = null,
    run_id = null
where locked_until is not null
  and locked_until < now();
```

Захват — один оператор:

```sql
update model_slots
set locked_by = $worker,
    locked_until = now() + make_interval(secs => $lease),
    run_id = $run
where slot_index = (
  select slot_index
  from model_slots
  where locked_by is null
  order by slot_index
  for update skip locked
  limit 1
)
returning slot_index;
```

Heartbeat и отпускание требуют тот же `locked_by`, тот же `run_id` и непустой лок. Ноль строк — слот уже не наш.

Отпускание происходит после возврата `ChatModel.complete` и до HTTP сервиса. Ожидание свободного слота крутится с паузой 1 с и с heartbeat запуска. Модель в этой паузе не вызывается.

### Данные и порядок

Живой чат по-прежнему один: `I6` и `409` с `reason: "dialog_busy"` для HTTP. Telegram по-прежнему может положить текст в буфер M2. Этот пункт буфер не меняет.

Два разных `chat_id` могут идти двумя процессами. Одновременных ответов модели не больше числа свободных слотов. Если процессов больше, чем слотов, лишний процесс держит свой запуск и ждёт слот. Если слотов больше, чем процессов, лишние строки простаивают. Хаб второе число из первого не выводит.

Потеря heartbeat слота не ставит запуск в `succeeded`. Просрочка слота только освобождает строку.

### Отказы

Нет свободного слота — ожидание, не отказ клиенту. Клиент уже получил id запуска.

Чужой `WORKER_ID` не продлевает слот. Расхождение `MODEL_SLOTS` и числа строк — отказ старта.

Ответ модели пришёл после потери слота: текст в `succeeded` не записывается. Если лок запуска жив, статус `failed`, ошибка `slot_lost`.

### Безопасность разработки

Тест слотов — два реальных соединения к базе `*_test`. Мок `postgres` не доказывает `SKIP LOCKED`. В тесте нет кода, который читает конфиг модели и сам решает, сколько вставок сделать, кроме явного числа фикстуры.

### Безопасность эксплуатации

Юниты воркера одинаковые, кроме `WORKER_ID`. Каждый смотрит только в `127.0.0.1` к Postgres и к LiteLLM. `ReadWritePaths` пуст относительно `FILE_ROOT` и `BLOB_ROOT`. Перезапуск одного экземпляра не помечает его запуск успешным: аренду снимет следующий reap.

Смена `MODEL_SLOTS` — действие человека: остановить воркеры, поменять свободные строки, поменять конфиг, запустить. Удалять строку с живым `locked_by` нельзя.

### Тесты

- два соединения берут два разных слота и не один;
- третий захват при двух строках получает пусто;
- просроченный `locked_until` снова свободен и `runs.status` не стал `succeeded`;
- heartbeat чужого воркера возвращает `false`;
- конфиг `2` при одной строке не пускает цикл;
- в коде захвата слота один `for update skip locked`;
- сервисный HTTP начинается только после отпускания слота;
- два запуска с одним `chat_id` не исполняются параллельно.

### Критерии готовности

По умолчанию один процесс и одна строка. Хаб не вычисляет предел модели. I13 соблюдён. I6 соблюдён. Потеря аренды слота не даёт `succeeded`.

## 4. Интерфейсы

Чат и голосовой ввод — клиенты хаба, рядом с Telegram. Один сценарий: отправил сообщение или файл, получил запуск, прочитал итог. Оболочки — веб, десктоп и телефон. Протокол к хабу один. Технологии оболочек выбираются отдельным пунктом, не здесь.

### Назначение

Клиент говорит с уже существующим HTTP. Новые маршруты — только файлы и привязка файла к постановке. Итог по-прежнему читается `GET /v1/runs/:id`.

Сейчас маршруты такие: `GET /health` без токена, `POST /v1/runs`, `GET /v1/runs/:id`. Хост `127.0.0.1`, порт `8787`. Тело JSON не больше 32 КиБ. `message` не длиннее 8000. `chat_id` приходит строкой. Неизвестные поля постановки схема отбрасывает, читая свои ключи. Ответы постановки: `201` и `reason: "created"`, `200` и `reason: "replay"`, `409` и `reason: "dialog_busy"` вместе с id. Ошибки — `{ "reason": "<код>" }` без стека. Сравнение bearer — `timingSafeEqual` при равной длине буферов. Пустой токен не подходит ни к какому заголовку.

Telegram остаётся процессом `telegram`. Он по-прежнему не вызывает модель. Файл, стикер и пустой текст по-прежнему не создают запуск. Приём файла ботом этот документ не добавляет.

### Чего в пункте нет

Нет выбора фреймворка оболочки, нет голосового движка, нет пользователей, нет OAuth, нет refresh-токенов, нет выноса бота.

### Критерии, после которых бота можно вынести

Вынос сейчас не делается. Он станет отдельной работой только когда одновременно верно всё:

- боту достаточно `POST /v1/runs`, `GET /v1/runs/:id` и `GET /health`;
- каталог `src/telegram` больше не нужен очереди, раннеру и модели, а сам не импортирует их;
- токен бота живёт только в окружении этого клиента;
- буфер занятого чата и отметка доставки либо выражены ответами HTTP, либо сознательно оставлены;
- файлы и голос боту по-прежнему не обещаны.

До этого он в поставке. Копирования истории сообщений документ не описывает.

### Угрозы

Второй токен клиента получает права первого после ротации. Токен попадает в URL и в журнал прокси. Оболочка зовёт сервис напрямую и обходит журнал. Повтор постановки создаёт второй запуск. Чужой `chat_id` в числовом JSON теряет точность. Большое тело маскируется под `application/json` и обходит лимит файла.

### Технологии

Тот же Hono и `node:http`. Новый npm-пакет для клиента не нужен. Заголовок `X-Content-Type-Options: nosniff` остаётся. `requestTimeout` 30 с и `headersTimeout` 10 с остаются для JSON. Загрузка файла — отдельный маршрут со своим потолком, потому что общий JSON-лимит 32 КиБ файл не перевозит. OWASP прямо разделяет лимиты по типу содержимого и требует сверять тело с `Content-Type`.

Учётные записи людей не вводятся. Сейчас секрет один: `HARNESS_API_TOKEN`. Расширение — файл хешей вне репозитория, режим `0600`. Элемент: `name` и `sha256`. Сырого токена в файле нет. Проверка: SHA-256 предъявленного bearer, затем `timingSafeEqual` с сохранёнными 32 байтами. Отзыв удаляет одну запись. Остальные хеши не меняются.

Пока в окружении задан прежний `HARNESS_API_TOKEN`, процесс на старте считает его хеш в память под именем `legacy` и дальше сравнивает только хеш. Пустое значение по-прежнему не открывает API. Значение в лог не пишется.

### Протокол

Уже существующие маршруты сохраняют коды и поля.

`POST /v1/runs` принимает прежние поля и необязательный `blob_ids`: массив uuid, не длиннее 8. Неизвестный другой ключ по-прежнему не мешает постановке. Неизвестный id файла, чужой `tenant_id` или просроченный файл — `400` и `reason: "invalid_body"`. В `payload` сохраняются `message` и, когда массив не пуст, `blob_ids`. Раннер добавляет к пользовательскому тексту строки `file <uuid> <bytes>` без пути на диске и без байтов.

Новая загрузка, не JSON:

`POST /v1/blobs`

- `Authorization: Bearer`
- `Content-Type: application/octet-stream`
- `Content-Length` обязателен
- необязательный `Idempotency-Key`, видимый ASCII, 1..256 символов

`201` и `{ "id", "bytes", "sha256" }`. Тот же ключ и тот же SHA-256 байтов — `200` и тот же id. Тот же ключ и другие байты — `409` и `reason: "idempotency_conflict"`. Больше потолка — `413`. Имя файла заголовком не принимается и путём не становится.

`GET /v1/blobs/:id` — метаданные, без байтов. `GET /v1/blobs/:id/content` — байты для клиентского bearer. Служебная способность на этом маршруте описана в пункте 5 и клиентским токеном не заменяется. Оба заголовка сразу — `400`.

Все ответы с `nosniff`. Тело ошибки без стека и без `DATABASE_URL`.

`source` новых клиентов остаётся `api`. Новое значение check-ограничения не добавляется.

### Данные и порядок

Постановка по-прежнему одна транзакция: блокировка ключа идемпотентности, затем живой `chat_id`, затем `insert`. Файл к этому моменту уже лежит в `BLOB_ROOT`, либо массива нет. Захват воркера идёт после ответа HTTP клиенту.

`chat_id` в запрос сервиса не копируется.

### Отказы

Нет bearer — `401`, включая `GET /health` как публичный единственный маршрут. Чужой токен — `401`. Отозванный хеш — `401`, остальные токены живы. Повтор ключа запуска — тот же id. Живой чат — `409` и id живого. Тело JSON больше 32 КиБ — `413` на постановке, даже если `Content-Type` объявлен как файл. Файл на маршрут постановки не принимается.

### Безопасность разработки

Секрет в репозиторий и в фикстуру, похожую на боевой ключ, не кладётся. В тестах строка вида `test-secret-value`. Оболочка в этот репозиторий не добавляется. Ревью смотрит, что API не импортирует `ChatModel` и клиент сервиса.

### Безопасность эксплуатации

Файл хешей вне каталога репозитория. Ротация одного имени не переписывает файл целиком с новыми секретами других имён: меняется одна строка хеша. Журнал HTTP хранит `run_id` и `reason`, не заголовок. Туннель, если он есть, заканчивается на `127.0.0.1:8787` и не заменяет bearer.

Копия базы без файла хешей оставляет API закрытым, пока оператор не положит хеши заново. Это ожидаемо.

### Тесты

- без токена `POST` даёт 401, `GET /health` даёт 200;
- второй именованный токен работает, удаление его хеша даёт 401, первый жив;
- повтор `idempotency_key` возвращает тот же запуск;
- живой `chat_id` даёт 409;
- `blob_ids` длиннее 8 отвергается;
- загрузка больше потолка даёт 413 и файл на диске не остаётся;
- тот же ключ загрузки и другие байты — 409 и один id;
- `chat_id` длиннее точного целого не проходит через `Number`;
- в ответе нет `Authorization` и нет байтов файла на `GET /v1/runs/:id`.

### Критерии готовности

Старые маршруты зелёные. Новые файловые маршруты требуют bearer. Пользователей и OAuth нет. Бот на месте. Технология оболочки не названа как выбранная.

## 5. Файлы

Клиент передаёт файл хабу. Хаб хранит его у себя и отдаёт сервису ссылку, не тело в контекст модели. Сервис возвращает короткий итог или новый файл. Дальнейшая работа с результатом в собственном интерфейсе сервиса идёт по тому же идентификатору.

### Назначение

`BLOB_ROOT` — каталог хаба, отдельный от `FILE_ROOT`. Байты лежат на диске. Метаданные — в Postgres хаба. В контекст модели входят id и размер. В сервис входит одноразовая способность, если манифест инструмента говорит `accepts_blobs: true`.

У трёх выносимых инструментов `accepts_blobs` равен `false`. Они работают с `FILE_ROOT` внутри сервиса. Способность и приём нового файла описаны здесь, потому что тот же контракт нужен следующему сервису. `read_file` не копирует рабочий файл в blob: длинный текст режется флагом `truncated`, как сейчас, но в модель после хаба входит не больше 8000 символов. Потолок чтения сервиса остаётся 64 КиБ.

### Чего в пункте нет

Нет общего хранилища с картинками M4, нет выдачи файла через Telegram, нет имени пользователя в пути, нет постоянного URL с секретом в query.

### Угрозы

Угадывание id, повтор способности, способность чужого сервиса или чужого запуска, путь `BLOB_ROOT-evil`, симлинк наружу, файл больше потолка, секрет способности в журнале, подмена `Content-Type` ради обхода лимита, SSRF: сервис отдаёт хабу свой URL вместо id.

### Технологии

Идентификатор файла — `crypto.randomUUID()`. Имя на диске — этот uuid, один сегмент. Каталог проверяется тем же кодом, что `security.mdc`: `realpath`, затем префикс с разделителем.

Способность — 32 байта `crypto.randomBytes`, в JSON кодировка base64url без `=`. В базе хранится SHA-256. Сырой токен в журнал не пишется. На время хода хаб добавляет выпущенные способности в список `redact`, чтобы эхо сервиса не дошло до модели.

Срок — 60 с, одна успешная выдача, привязка к `service_id` и `run_id`. Это не ссылка в query: секрет в URL попадает в журнал прокси. Выдача идёт заголовком `X-Capability`.

Потолок по умолчанию — 32 МиБ. Конфиг не может поднять его выше 128 МиБ: старт падает. Срок хранения — 7 суток от `now()`.

### Протокол способности

Хаб выпускает способность только пока держит лок этого запуска и только на blob этого `tenant_id`, который либо указан в постановке, либо принят от этого же запуска.

Сервис забирает байты так:

`GET /v1/blobs/:id/content`

- `Authorization: Bearer <долгий секрет сервиса>`
- `X-Capability: <одноразовый токен>`

Оба должны сойтись со строкой: сервис, запуск, файл, `used_at is null`, `expires_at > now()`. Отметка `used_at` ставится в той же короткой транзакции до потока байтов. Вторая выдача — `401` и `reason: "capability_used"`. Просрочка — `401` и `reason: "capability_expired"`. Чужой сервис, чужой запуск и неверный токен — `404` и `reason: "not_found"`, чтобы не подтверждать чужой id. Клиентский bearer вместе со способностью — `400`.

Новый файл от сервиса:

`POST /v1/blobs/ingest`

- долгий bearer сервиса;
- `Idempotency-Key: <run_id>:<tool_call_id>`;
- заголовки `X-Run-Id` и `X-Tool-Call-Id` совпадают с ключом;
- тело `application/octet-stream` не больше потолка;
- лок запуска ещё у этого воркера, иначе `409`.

Ответ `201` и `{ "id", "bytes", "sha256" }`. Id возвращается в массиве `blobs` ответа инструмента. Хаб проверяет, что id создан этим запуском. Чужой id — отказ разбора ответа, модели он не отдаётся.

Дальше человек читает тот же id клиентским bearer. Сервис свой экран не получает от хаба.

### Данные

Миграция `migrations/010_blobs.sql`, файл не создаётся этим документом.

Таблица `blobs`: `id`, `tenant_id`, `sha256`, `byte_size`, `media_type`, `created_at`, `expires_at`, необязательный ключ идемпотентности и хеш тела. `media_type` хаб ставит сам: `application/octet-stream`. Чужой тип не становится путём и не становится HTML.

Таблица `blob_capabilities`: `id`, `blob_id`, `token_sha256`, `service_id`, `run_id`, `expires_at`, `used_at`.

`runs.payload` уже jsonb. Отдельная колонка под id файлов не нужна. Колонка `run_steps.duration_ms` — миграция `migrations/011_step_duration.sql`, целое не меньше нуля, иначе `null`. Старые миграции не переписываются.

Удаление просроченных файлов — короткий запрос не больше 20 строк за проход процесса, который и так обслуживает очередь. Сначала строка, потом файл под `BLOB_ROOT` после `realpath`. Отдельный крон не заводится. Файл без строки и строка без файла на следующем проходе расходятся в безопасную сторону: лишний файл удаляется только если путь внутри корня, отсутствующий файл становится ошибкой чтения.

### Порядок относительно захвата

Клиент загружает байты до постановки либо не загружает их. Постановка коммитится без держания байтов в транзакции: в транзакции только проверка id. Захват запуска коммитится до модели. Способность вставляется коротким оператором уже во время хода, после захвата, и коммитится до HTTP сервиса. Поток байтов транзакцию не держит.

### Отказы

Таймаут чтения способности — ошибка инструмента. Новая способность на тот же вызов сама не выпускается: потолок выпусков на пару blob и tool call равен 1. Сервис, который не успел, возвращает ошибку, запуск жив.

Потеря лока до ingest — `409`, байты, если уже писались во временный файл, удаляются. Повтор того же ключа и того же хеша возвращает первый id.

Тело больше 32 МиБ режется по счётчику байтов, даже если `Content-Length` меньше. Несовпадение длины — `400`, файл не сохраняется.

### Безопасность разработки

Тесты пути живут рядом с хранилищем и используют временный каталог. Боевой `BLOB_ROOT` тест не трогает. В фикстуре нет настоящего секрета. Ревью смотрит, что способность не попадает в `request_excerpt`.

### Безопасность эксплуатации

`BLOB_ROOT` есть только у процесса `api` в `ReadWritePaths`. Воркер и файловый сервис каталог не монтируют на запись. Режим каталога не даёт читать его всем пользователям машины.

Копия: база хаба и `BLOB_ROOT` снимаются вместе. Иначе клиент видит id без байтов.

Ротация долгого секрета сервиса гасит уже выпущенные способности на следующем запросе, потому что bearer сервиса тоже проверяется. Клиентские хеши при этом не крутятся.

Лог: id файла, `run_id`, код отказа. Не байты, не `X-Capability`, не SHA, если он ещё не публичный ответ владельцу. Клиенту свой `sha256` в ответе загрузки отдаётся: это его файл.

### Тесты

- путь `../`, абсолютный, симлинк наружу и префикс `BLOB_ROOT-evil` не читаются;
- второй redeem — `capability_used`;
- просрочка — `capability_expired`;
- чужой `service_id` и чужой `run_id` — `404`;
- сырого токена нет в `run_steps` и в pino-записи теста;
- файл 32 МиБ + 1 байт не сохраняется;
- конфиг 129 МиБ не даёт процессу стартовать;
- тот же ключ ingest и другой хеш — 409 и один файл;
- байты файла отсутствуют в сообщении, которое тестовая модель получила следующим ходом;
- `chat_id` в теле вызова сервиса отсутствует.

### Критерии готовности

Модель не получает тело файла. Сервис без `accepts_blobs` не получает способность. Одноразовая способность живёт 60 с и привязана к сервису и запуску. `FILE_ROOT` и `BLOB_ROOT` не совпадают. I19 для обоих корней соблюдён там, где корень открывается.

## 6. Телефон

Путь от телефона до машины, где стоит хаб, — отдельный безопасный туннель. Контракт сервиса про туннель не знает: к моменту вызова канал между хабом и сервисом уже есть.

Поставить хаб на телефон с маленькой моделью можно отдельно. Контракт тот же. Обязанность каждого сервиса самому строить защищённое соединение с телефоном в контракт не входит.

Постановка хаба на телефон раскрыта в конце файла. Здесь — путь от телефона к хабу на своей машине.

### Назначение

Туннель заканчивается на машине хаба соединением к `127.0.0.1:8787`. Приложение телефона — клиент HTTP из пункта 4. Сервисы туннель не видят и адрес телефона не получают.

### Чего в пункте нет

Продукт туннеля не выбран. Нет настройки конкретного клиента, нет ключей в этом файле, нет проброса Postgres, LiteLLM, файлового сервиса и порта картинок.

### Угрозы

Хаб публикуют на `0.0.0.0`, чтобы «починить телефон». Туннель пробрасывает диапазон портов, и с телефона открывается база или шлюз модели. Bearer кладут в URL туннеля. Журнал туннеля хранит заголовок и тело. Отзыв телефона крутит все токены. Компрометация туннеля без bearer считается достаточным входом в API. Сервис начинает слушать телефон, хотя контракт этого не требует.

### Технологии

Любой будущий продукт обязан выполнить требования ниже. Документ не сравнивает продукты и не назначает один из них.

Хаб уже отвергает чужой адрес прослушивания константой `API_LISTEN_HOST`. Это остаётся. Менять её на внешний интерфейс ради туннеля нельзя.

Если продукт туннеля сам использует TLS, проверка сертификата на телефоне включена. `rejectUnauthorized: false` на клиенте телефона запрещён так же, как на хабе.

### Требования к туннелю

- Шифрование на всём пути от телефона до машины хаба. Открытый трафик через чужую сеть не годится.
- Оба конца узнают друг друга. Факт «пакет дошёл» входом не считается.
- Вход в API всё равно требует bearer. Туннель его не заменяет.
- Отзыв одного устройства не меняет хеши других клиентов и не меняет секрет сервиса.
- Отзыв одного именованного токена не обязан рвать туннель другого устройства.
- Наружу машины не публикуются порт хаба, порт базы, порт шлюза модели и порт файлового сервиса. Соседние локальные сервисы тоже не пробрасываются. Наружу смотрит только порт самого туннеля, если продукту он нужен, и этот порт не является портом хаба.
- Проброс — один адрес назначения, `127.0.0.1:8787`. Не подсеть и не диапазон.
- Телефон не открывает слушатель для сервисов хаба. Сервис не получает адрес телефона.
- В журнал туннеля не входят bearer, тело, байты файла и `DATABASE_URL`. Допустимы время, id устройства и код отказа.
- Секрет API не записывается в конфиг туннеля и не вставляется в ссылку или QR как токен HARNESS. Ключ устройства, если он есть, — другой секрет и лежит в хранилище ОС телефона.
- Обрыв туннеля не ставит запуски в `succeeded`. Их аренду снимет обычный reap.

Текущая проверка URL в API собирает адрес из пути и ждёт хост `127.0.0.1`. Её не ослабляют ради имени туннеля в заголовке `Host`.

### Данные и порядок

Телефон вызывает тот же `POST /v1/runs`. Дальше захват, модель и сервис идут на машине хаба так же, как для локального клиента. К моменту HTTP сервиса туннель уже ни при чём: сервисный вызов на `127.0.0.1` машины хаба либо в частную сеть по правилам пункта 1.

### Отказы

Туннель не поднят — клиент получает отказ сети. Запуск не создаётся, потому что постановка не дошла. Дошедшая постановка живёт своей арендой, даже если телефон ушёл в сеть. Итог телефон прочитает повторным `GET`, когда путь вернётся. Второй `idempotency_key` не нужен: повтор вернёт ту же строку.

Подмена назначения туннеля на чужой порт — ошибка установки, не режим работы. Хаб её не «принимает» сменой адреса.

### Безопасность разработки

В репозиторий не кладут конфиг туннеля с ключами. Тест хаба поднимает клиент на `127.0.0.1` и не имитирует продукт туннеля. Ревью отвергает патч, который меняет `API_LISTEN_HOST` или добавляет слушатель на все интерфейсы.

### Безопасность эксплуатации

Оператор хранит ключи устройств в хранилище, которое уже есть у выбранного позже продукта, и отдельно хранит хеши bearer. Потеря телефона: отозвать устройство и удалить один хеш. Остальные клиенты и сервисы не перевыпускаются.

Резервная копия хаба не содержит приватный ключ туннеля в дампе базы: этому ключу в Postgres места нет.

На хосте файрвол не пускает на внешний интерфейс порты хаба и баз. Это дублёр к bind на лупбэк, не повод открыть bind.

### Тесты

- процесс API не слушает `0.0.0.0`, и попытка сконфигурировать такой хост падает;
- запрос без bearer с локального порта получает 401;
- в коде вызова сервиса нет адреса телефона и нет чтения конфига туннеля;
- отзыв одного хеша не меняет второй;
- `GET /health` с лупбэка остаётся 200.

### Критерии готовности

Контракт сервиса не упоминает туннель. Хаб слушает только `127.0.0.1`. Продукт туннеля в документе не выбран. Телефон не становится обязательным входящим адресом для сервисов.

## 7. Разработка через pull request

Работа входит только через pull request. Прямой push в долгие ветки закрыт.

Ветки идут цепочкой `prod` ← `stage` ← `dev` ← короткая ветка. Короткая ветка — `feature`, `bugfix` или `hotfix`. Обычная задача сливается в `dev`, оттуда в `stage`, оттуда в `prod`. `hotfix` начинается от `prod` и после починки возвращается вниз, в `stage` и `dev`, чтобы исправление не потерялось.

Пайплайн GitHub — последовательность ворот. Следующие ворота не открываются, пока предыдущие не прошли:

1. тесты;
2. Bandit;
3. SonarQube;
4. Trivy: уязвимости и SBOM. Отчёт SBOM сохраняется артефактом, его можно скачать.

Автоматическое ревью pull request делает ИИ. Замечание ИИ человек может принять или снять с записью, почему. Слияние без человека не проходит.

Локально Husky вешает хуки. `pre-commit` гоняет ESLint по изменённым файлам и не пускает коммит с ошибкой. `pre-push` гоняет проверку типов и тесты и не пускает push с ошибкой. ESLint и тесты в репозитории уже есть. Этот пункт подключает их к хукам и к первым воротам пайплайна, а не заводит второй набор правил.

Bandit смотрит Python. В текущем репозитории его нет: код на TypeScript, и близкую проверку уже делает `eslint-plugin-security`. Шаг Bandit в пайплайне стоит для Python-сервисов, которые появятся рядом. Пока Python нет, шаг пустой и зелёный, TypeScript он не притворяется проверять.

Рядом с Trivy на тех же воротах стоит поиск секретов в дереве. Находка секрета останавливает pull request так же, как высокий уровень уязвимости. Порог, который именно ломает сборку, и адрес SonarQube выбираются в подробном плане этого пункта.

### Назначение

Этот пункт закрывает вход в долгие ветки репозитория HARNESS. Код продукта он не меняет. Каждый сервисный репозиторий повторяет те же ворота у себя. Пока Python живёт отдельным репозиторием, шаг Bandit в HARNESS пустой. В репозитории Python-сервиса тот же шаг уже запускает Bandit и пустым не считается.

### Чего в пункте нет

Нет второго ESLint, нет продукта туннеля, нет выбора оболочки и голоса, нет ключа модели в секретах репозитория ради ревью, нет выдуманного URL SonarQube.

### Угрозы

Прямой push в `prod`. Force-push стирает ревью. Администратор обходит ruleset. Секрет в дереве проходит, потому что ворота смотрят только уязвимости пакетов. Bandit «проверяет» TypeScript и рисует зелёный крест. Sonar молча пропускает сборку, когда сервер недоступен. SBOM не скачать. ИИ одобряет PR вместо человека. `HUSKY=0` воспринимается как отмена CI. Журнал Actions печатает найденный секрет.

### Технологии

Долгие ветки закрывает ruleset GitHub. Нужные правила из [документации ruleset](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets): pull request перед слиянием, одна одобряющая ревью человека, погасшие одобрения после нового push, обязательное разрешение тредов, обязательные status checks, запрет force-push, запрет удаления ветки. Список обхода пуст, включая администраторов. GitHub предупреждает: без обхода ветку по умолчанию не переименовать. Этот пункт переименование не делает, постоянный обход не заводится.

Короткие ветки: `feature/*`, `bugfix/*`, `hotfix/*`. Обычный PR идёт в `dev`. Продвижение — отдельный PR `dev` → `stage` и отдельный PR `stage` → `prod`, те же ворота. `hotfix/*` ответвляется от `prod`, сливается в `prod` тем же PR, затем отдельными PR возвращается в `stage` и в `dev`.

Ветка `main` в этом плане не участвует. Её не переименовывают, не включают в ruleset и не связывают с `prod`, `stage` и `dev`. Обновляет её человек вручную, когда сам решит.

Хуки — Husky 9. Точный номер фиксирует `package-lock.json` в момент подключения, не `*` и не `latest`. Скрипт `prepare` ставит хуки. В CI переменная `HUSKY=0`, чтобы установка на раннере не подменяла ворота. Обход хука флагом `--no-verify` локально возможен и поэтому границей не считается. Граница — красные ворота и ruleset.

`pre-commit` вызывает `node` на скрипт. Скрипт читает индекс через `git diff --cached -z` и передаёт имена файлов массивом аргументов в уже существующий ESLint. Строка оболочки из имён файлов не собирается. Конфиг — текущий `eslint.config.js`. Правила `security/detect-child-process`, `security/detect-eval-with-expression`, `security/detect-non-literal-regexp` и `security/detect-unsafe-regex` остаются ошибками.

`pre-push` запускает уже существующие `npm run typecheck` и `npm test`.

Ворота — один workflow с `needs`, чтобы следующая работа не началась при красной предыдущей:

1. `test` — `npm test` и отчёт покрытия lcov;
2. `bandit` — после тестов;
3. `sonarqube` — после Bandit, забирает lcov;
4. `trivy` — после SonarQube: уязвимости, секреты, затем SBOM.

Сторонний action закрепляется полным SHA коммита на момент подключения. Плавающий тег не используется. `permissions` workflow — чтение содержимого. Секреты в лог не печатаются.

ИИ-ревью — CodeRabbit. Человек подключил его через мастер https://app.coderabbit.ai/wizard. CodeRabbit пишет замечания в pull request. Проверка `ai-review` — опубликованный результат CodeRabbit, не вечная красная заглушка. Имя модели документ не выбирает: ключа модели в дереве нет, и заводить его ради ревью нельзя. У App нет права approving review. Одобрение человека — отдельное обязательное ревью. Ruleset не считает CodeRabbit тем, кто имеет право одобрить. Замечание принимается ответом в треде и resolve. Снятие — тот же тред с непустой причиной, почему замечание неверно, затем resolve. Пустой resolve без текста причиной не считается. Это правило ревью, не второй линтер.

### Порог, который ломает сборку

SonarQube. Workflow и `sonar-project.properties` адрес не содержат. URL хранится переменной GitHub `SONAR_HOST_URL`. Токен анализа — секрет `SONAR_TOKEN`. Чужой CA, если он есть, — секрет `SONAR_ROOT_CERT`. Токена и сертификата в git нет. Пустая переменная, обрыв TLS или отказ сервера красят ворота. Сканер ждёт ворота флагом `sonar.qualitygate.wait=true`. Таймаут ожидания — 300 с, штатный для сканера. Не дождался — шаг красный.

Ворота называются `harness`. На сервере заводятся свои ворота с этим именем, не молчаливое ослабление готовых Sonar way.

Сборка ломается, если на новом коде PR верно любое условие:

- новых уязвимостей больше 0;
- новых багов больше 0;
- новые security hotspots разобраны меньше чем на 100%;
- покрытие нового кода ниже 80%;
- плотность дублирования нового кода выше 3%.

80% и 3% — рекомендуемые условия Sonar way из [описания quality gates](https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates). Условие «любое новое замечание» оттуда не берётся. Запахи кода и оценка сопровождаемости сборку не ломают: их уже держат ESLint и `tsc`. Если сервер в режиме MQR и отдельные счётчики багов не показывает, те же ворота задаются так: оценка надёжности нового кода хуже A, оценка безопасности нового кода хуже A, покрытие и дублирование как выше. Оценка сопровождаемости в ворота не ставится. Старый код целиком ворота PR не красит: на pull request Sonar смотрит новый код.

Покрытие считается, только если тесты выгрузили lcov. Для этого к dev-зависимостям добавляется провайдер покрытия той же линии `vitest`, версия записывается точно. Нет отчёта — покрытие выглядит нулевым, ворота красные.

Trivy. Уязвимости: `trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1`. `MEDIUM` и ниже сборку не ломают. `--ignore-unfixed` не ставится: неисправленные `HIGH` и `CRITICAL` тоже ломают. Номер релиза Trivy в workflow конкретный, не `latest`. Образ сканирования нет: Docker этот документ не требует, смотрится дерево и lockfile.

Секреты на тех же воротах, отдельной командой: `trivy fs --scanners secret --exit-code 1`. Любая находка ломает PR так же, как `HIGH`. Исключения только для фикстуры `test-secret-value` и для пустых значений в `.env.example`. JSON этого шага артефактом не публикуется и в конце шага удаляется. В лог шага входят путь и код правила, не само значение.

SBOM: `trivy fs --scanners vuln --format cyclonedx -o sbom.cdx.json`. Формат CycloneDX по [документации Trivy](https://github.com/aquasecurity/trivy/blob/main/docs/guide/supply-chain/sbom.md) по умолчанию описывает состав, не список уязвимостей. Сканер секретов в эту команду не включён. Файл — артефакт workflow, хранение 90 суток, его можно скачать. Ошибка записи файла красит шаг.

Bandit. Нет файлов `*.py` — шаг пишет `no python` и кончается нулём. TypeScript он не запускает. Появился `.py` в этом репозитории — шаг перестаёт быть пустым и гоняет Bandit с порогом не ниже medium по серьёзности и уверенности (`-ll` и `-ii` в [справочнике Bandit](https://bandit.readthedocs.io/en/latest/man/bandit.html)). `--exit-zero` запрещён. Версия Bandit в этот момент пишется явно. Пока Python вынесен отдельным репозиторием, там этот шаг с первого дня не пустой.

`.trivyignore` в начале пуст. Новая строка видна в diff. Человек в треде пишет, зачем она. Без этой записи одобрение человека не ставится.

### Факты установки

Продукт ИИ-ревью — CodeRabbit, не локальный LiteLLM. Человек подключил его сам. CodeRabbit пишет замечания, снимает их человек. Обязательное одобрение pull request остаётся за человеком. Ruleset не считает CodeRabbit тем, кто имеет право одобрить.

Фактические права GitHub App на `SanteraSan/HARNESS` не прочитаны. `gh` авторизован как `SanteraSan`, у репозитория право ADMIN. `GET /user/installations` вернул 403: токен пользователя не является user-to-server токеном GitHub App. `GET /repos/SanteraSan/HARNESS/installation` вернул 401: нужен JWT приложения. Страница установок в браузере открылась формой входа, сессии не было. Ruleset репозитория пуст, защиты ветки нет, комментариев CodeRabbit в репозитории нет. Настройки в облаке CodeRabbit не менялись. Право approve, merge или администрирования, если оно выдано, не снималось: его не было видно.

SonarQube — Community Build. Сервер и его поиск слушают только локальный адрес, не внешний интерфейс. Процесс идёт не от root. В юните включены `NoNewPrivileges` и `ProtectSystem=strict`. Каталог сервера лежит вне репозитория. Линейка требует JDK 21 или 25, не JRE из архива. Имя юнита, путь к нему и порты этой машины в документ не пишутся.

База — отдельный PostgreSQL, не `harness` и не `harness_test`. Роль без суперпользователя, кодировка UTF8. Имя контейнера и порт в этот файл не пишутся. Пароль администратора Sonar сменён. Пароль и токен лежат вне репозитория, в файле с правами `0600`. В git и в этот файл они не копируются. Секрет GitHub `SONAR_TOKEN` записан. Переменная GitHub `SONAR_HOST_URL` указывает на локальный сервер. Значение адреса в репозитории не хранится.

Режим сервера — MQR. Ворота `harness` назначены трём проектам и не ослабляют встроенные Sonar way: условие «любое новое замечание» (`new_violations`) в эти ворота не входит, оценка сопровождаемости не входит. Сборка ломается, если на новом коде верно любое условие: `new_bugs` больше 0, `new_vulnerabilities` больше 0, `new_software_quality_reliability_rating` хуже A, `new_software_quality_security_rating` хуже A, `new_security_hotspots_reviewed` меньше 100, `new_coverage` меньше 80, `new_duplicated_lines_density` больше 3. Период нового кода экземпляра — `PREVIOUS_VERSION`.

[Таблица сравнения редакций](https://docs.sonarsource.com/sonarqube-community-build/feature-comparison-table) для Community Build: анализ веток — только основная ветка проекта, анализ pull request — недоступен, отчёт статуса ворот на pull request — недоступен. [Разбор в GitHub Actions](https://docs.sonarsource.com/sonarqube-community-build/devops-platform-integration/github-integration/adding-analysis-to-github-actions-workflow) говорит не анализировать несколько веток одного проекта и не ставить событие `pull_request`. Поэтому Sonar принимает `dev`, `stage` и `prod` как проекты `harness-dev`, `harness-stage` и `harness-prod`. Украшение pull request не обещается. На pull request остаются тесты, Bandit и Trivy; их workflow этим шагом не добавлялся. Сканер ждёт ворота флагом `sonar.qualitygate.wait=true`. Ветка `main` не используется и не создавалась.

Workflow `.github/workflows/sonarqube.yml` запускается только на push в `dev`, `stage` и `prod`, на self-hosted раннере с меткой `harness-sonar`. `pull_request_target` нет. Раннер не зарегистрирован. Регистрация от учётной записи с доступом к `.env` HARNESS и к базам `harness` / `harness_test` дала бы заданию этот доступ, поэтому она не делалась и успехом не считается. Отдельный пользователь без этого доступа ещё не заведён.

### Данные и порядок

PR в короткую ветку проходит четыре ворота по очереди, затем ревью ИИ, затем одобрение человека. Следующая ступень цепочки — новый PR, не push. Красные ворота не «переезжают» на stage.

Хуки локально стоят раньше push. CI их не заменяет и ими не заменяется.

### Отказы

Упал тест — Bandit не стартует. Упал Bandit — Sonar не стартует. Упал Sonar — Trivy не стартует. Секрет, `HIGH` или `CRITICAL` — PR закрыт для слияния. Недоступный Sonar — красный шаг, не пропуск. ИИ недоступен — проверка `ai-review` красная. Одобрение бота человеком не считается.

`hotfix` те же ворота не отключает.

### Безопасность разработки

Workflow не содержит значений секретов. `SONAR_TOKEN` маскируется GitHub. В репозиторий не добавляется второй набор правил ESLint. `eslint-disable` без причины в отчёте PR не оставляется, как и раньше. Фикстуры тестов не становятся похожими на боевые ключи ради зелёного сканера: исключение одно и узкое.

Ревью человека смотрит ещё и diff зависимостей. Новый runtime-пакет хаба вне уже закрытого списка этим пунктом не оправдывается. `husky` и провайдер покрытия — devDependencies.

### Безопасность эксплуатации

Секреты CI живут в GitHub, не в юнитах хаба и не в `BLOB_ROOT`. Ротация `SONAR_TOKEN` не крутит `HARNESS_API_TOKEN` и не крутит секрет сервиса.

Артефакт SBOM может перечислять версии пакетов. Это принимается: его и просили скачивать. Туда не кладут `.env` и вывод секретного сканера.

Если раннер GitHub чужой, дерево сборки всё равно не должно содержать боевой `.env`. Тесты ходят в базу только там, где оператор сам дал секрет тестовой базы. Боевая база `harness` в CI не используется. Имя тестовой базы кончается на `_test`.

Падение ворот не трогает уже запущенные процессы хаба. Деплой этим пунктом не описывается.

### Тесты

- скрипт pre-commit на файле с ошибкой ESLint кончается ненулём и не зовёт оболочку с подставленным именем;
- чистый файл скрипт пропускает;
- pre-push вызывает те же команды, что `typecheck` и `test`;
- в workflow есть цепочка `needs` в порядке тесты, Bandit, Sonar, Trivy;
- репозиторий без `*.py`: команда шага Bandit кончается нулём и не вызывает исполнимый файл Bandit;
- пример с `test-secret-value` попадает в узкое исключение, а пример формата боевого ключа в исключение не входит;
- в workflow нет строки `0.0.0.0` и нет `rejectUnauthorized: false`.

Живой Sonar и живой GitHub в `npm test` не требуются.

### Критерии готовности

Прямой push в `dev`, `stage` и `prod` закрыт ruleset, когда оператор его включил. Ветка `main` в этом плане не участвует. Её не переименовывают, не включают в ruleset и не связывают с `prod`, `stage` и `dev`. Обновляет её человек вручную, когда сам решит. В репозитории есть хуки и workflow с четырьмя воротами в заданном порядке. Пороги выше записаны в конфиг ворот и в команды Trivy. В workflow и в `sonar-project.properties` URL нет. Слияние без человеческого approving review невозможно. TypeScript через Bandit не прогоняется.

## Следующий пункт: оболочки и голос

Технология оболочки и движок распознавания речи здесь не выбираются. Ниже — требования, которые обязан выполнить любой будущий стек. Веб, десктоп и телефонное приложение этим разделом не назначаются.

Оболочка — клиент HTTP хаба из пункта 4. Она не открывает Postgres, не читает `FILE_ROOT` и `BLOB_ROOT`, не хранит секрет сервиса и не вызывает сервис напрямую.

Bearer не попадает в URL, в репозиторий оболочки, в текст модели и в журнал оболочки. На телефоне он лежит в хранилище секретов ОС. На других оболочках — в хранилище секретов той платформы, которую выберут позже. Файл с сырым токеном в дереве проекта не хранится.

Текст модели и текст инструмента показываются как простой текст. Они не исполняются как HTML, скрипт, `eval` или `new Function`. Electron, IPC и `executeJavaScript` к этому репозиторию не относятся и этим пунктом не выбираются.

Файл уходит в `POST /v1/blobs`. В `message` попадают id, которые вернул хаб, а не байты. Длина сообщения — те же 8000 символов. Оболочка не поднимает потолки хаба.

Голос. Микрофон выключен, пока человек сам не начал ввод. В запуск уходит текст расшифровки той же постановкой `POST /v1/runs`, с тем же лимитом 8000. Аудио не является аргументом инструмента и не подмешивается в контекст модели как байты. Этот документ не решает, распознавание на устройстве или снаружи. Если будущий движок отправляет звук наружу, это отдельное решение со своей угрозой: звук — содержимое пользователя, bearer в него не кладётся, и этот файл такое решение не принимает.

Оболочка не слушает `0.0.0.0`. Если она говорит с хабом не через лупбэк, путь — туннель из пункта 6, с проверкой TLS, без отключения проверки сертификата. Пользователей и OAuth оболочка не заводит.

Журнал оболочки не хранит тело файла, заголовок Authorization и сырой ответ шлюза модели. Стек для этого журнала тоже не выбирается.

## Хаб на телефоне

Отдельная поставка, не флаг серверной установки. Контракт тот же: `harness.tool.v1` и HTTP клиента из пункта 4.

`MODEL_SLOTS` у этой поставки равен 1. Процесс воркера один. Хаб и здесь не вычисляет `num_parallel`.

Секреты лежат в хранилище ОС телефона: bearer клиента, если он нужен локальному UI, и секрет сервиса, если локальный сервис вообще есть. В репозиторий приложения и в текст модели они не входят.

Входящего слушателя с телефона в сервисы нет. Сервис не обязан и не имеет права сам устанавливать канал до телефона. Если телефонный хаб зовёт сервис, это исходящий вызов по правилам пункта 1: лупбэк телефона либо частный адрес с TLS, приколотым сертификатом и bearer. Чужой сервис не подключается к телефону.

Наружу телефон не публикует порт хаба, порт базы и порт сервиса. Туннель из пункта 6 для этой поставки не становится обязанностью серверных сервисов.

Стек мобильного UI не выбирается. Маленькая модель — решение установки. Учёт токенов делает хаб по ответу того шлюза, который поставлен рядом. Сервис по-прежнему не объявляет чужие токены.

Потеря процесса снимает аренду обычным сроком. Успешный статус из обработчика закрытия приложения не ставится.
